# Contributing

The project was built in milestones: Milestone 0 tested what each harness can do, and Milestones 1–7 built the broker, the web UI, the CLI, the agent MCP server, the hooks, `switchboard install` / `uninstall` (`install` and the per-session MCP server and hook script are retired since 0.38.0, #385: agents connect over HTTPS), the delivery engine, per-harness delivery and `switchboard report`; Milestone 8 added remote members over SSH (retired in 0.38.0, #385: agents connect over HTTPS now). The milestones and their acceptance criteria are in [DESIGN.md §13](docs/DESIGN.md#13-milestones-and-acceptance-criteria), the Milestone 0 results in [docs/FINDINGS.md](docs/FINDINGS.md), and the M7 live rehearsal (Claude, Codex and Devin together in one room) in [docs/M7-REPORT.md](docs/M7-REPORT.md). Each change adds its release notes as a file in [`changes/`](changes/README.md), and updates the README or the docs it touches. A pull request that changes anything a person sees shows it: screenshots in its description, before and after, made with `docs/media/ui_shots.py` or `docs/media/cli_shots.py` (see [CLAUDE.md](CLAUDE.md) for where the images go).

**Changes come as pull requests,** from a branch here or from a fork, and the maintainer reviews and merges each one. If a coding agent writes yours, point it at [CLAUDE.md](CLAUDE.md): how a change lands, where the code and the tests live, and what has to be right. The same file is for people.

## Development

Development needs uv 0.7.13 or newer: `pyproject.toml` sets `[tool.uv] required-version = ">=0.7.13"`. CI and the Linux test container stay on 0.7.13 with `--frozen`, so a newer uv that would change `uv.lock` fails CI instead of slipping through (uv 0.12 re-locks the current lock unchanged).

**Dev mode (like `pip install -e`).** Either run from the checkout with `uv run switchboard start` (the project `.venv` from `uv sync` is already editable), or make the global command point at the checkout with `uv tool install --editable .`. Then:
- web UI changes (`src/switchboard/web/static/`): just refresh the browser, since the files are served from disk with `no-cache`;
- Python changes: restart the broker, `switchboard stop && switchboard start` (only one broker runs per home, so stop an installed one first);
- An agent connects over HTTPS with an agent token and switchboard's plugin, so nothing of this checkout runs on its side. Run a regular install (`uv tool install --reinstall .`) for a broker you leave running, so an agent editing this repo can't change it.

`uv sync` (project-local `.venv`), then `uv run pytest -q -n auto` runs the unit and integration tests in parallel on every core (about 2,500 tests in about 3 minutes, or about 9 without `-n auto`, including a 200-seed property test of the delivery rules; the integration tests start in-process brokers and scripted agents that call them over HTTPS, as an agent does). A test that leaves behind an object whose `__del__` raises — a resource forgotten to close, such as the leaked asyncio transport in #276 — fails too, in the test that leaked it: `pyproject.toml`'s `filterwarnings` turns `PytestUnraisableExceptionWarning` into an error, and `tests/conftest.py`'s `fail_on_unraisable_exception` (autouse) collects generations 0 and 1 after every test so the object is reclaimed there rather than in whichever later test the collector happens to next run in (issue #277; a full `gc.collect()` there instead measured at ~0.25s per test, about 13 minutes over this suite, against ~1ms for generations 0 and 1 alone, since gen 2 holds every object the process has ever promoted and a leaked object hasn't survived a collection yet). Strict timing checks are marked `perf` (`uv run pytest -m perf`). **Lint and static analysis:** `uv run python scripts/lint.py` runs Ruff, mypy, ESLint, ShellCheck and actionlint. Add `--fix` to format the Python tree and apply safe ESLint fixes. Node 22 is needed; ESLint's npm dependencies are locked in `scripts/eslint/`, and the script downloads checksum-verified ShellCheck and actionlint into ignored `.lint-tools/`. No Ruff or mypy findings are pinned (there is no `.lint-baseline.json`); new Python findings fail. The formatter checks the whole Python tree. CI runs the same command in a parallel `lint` job for code PRs.

**The plugins' scripts** exist twice for Claude Code: `sh` and `curl` for Linux and macOS (`plugins/claude/bin/listen`, `session`), and PowerShell for Windows (`plugins/claude/bin/windows/`, DESIGN.md §49.5). The tests that run them (`tests/integration/test_agent_plugins.py`) run each against both, the PowerShell ones under `pwsh` (PowerShell 7) when it is on PATH; without it they are skipped, but with `SWITCHBOARD_REQUIRE_PWSH=1` (set in CI, whose runners have it) a missing `pwsh` fails the run instead. A change to a PowerShell script is also run under Windows PowerShell 5.1 on a Windows machine, which no CI job has: keep the files ASCII and free of PowerShell 7-only syntax (a test checks both). The helper that makes Claude Code's listener key (`plugins/claude/bin/headers`, DESIGN.md §49.11) has its twin too: Claude Code runs a `headersHelper` with `cmd.exe` on Windows, which finds `bin/headers.cmd`, which starts `bin/windows/headers.ps1`. Its tests (`tests/integration/test_claude_plugin_signin.py`) run the helper and the listener's and session script's key use once for each implementation, and `tests/integration/test_claude_plugin_windows.py` checks what only Windows does (the access list that stands in for mode 0600, the walk to Claude Code's pid) in the source, so a change to either is also run on Windows by hand.

**Security reports:** `uv run python scripts/security_scan.py` runs Bandit on Python, pip-audit on every pinned package exported from `uv.lock`, an OSV query for the vendored Mermaid version, and zizmor on workflows. Findings print a count and do not fail the command; scanner errors do fail it. `--out DIR` keeps the JSON/SARIF files. The parallel `security.yml` workflow adds CodeQL (Python, JavaScript and Actions), Trivy on a freshly built image, and gitleaks on the full Git history; it redacts secrets and removes author details from the saved report. Open the run's artifacts to read the full reports. These jobs run on code PRs and `main`; docs-only and release changes skip them. They do not upload to code scanning and are not in the required `CI` aggregate. Fix a finding in its own PR, or document why it is a false positive; there is no suppression baseline or severity gate yet (DESIGN.md §36).

**The web UI** has three layers of tests. The node tests (`tests/unit/test_web_markdown.py`, `test_web_app_behavior.py`) run `md.js` and `app.js` in node against a fake DOM, in the default suite; without `node` on PATH they are skipped, but with `SWITCHBOARD_REQUIRE_NODE=1` (set in CI, which installs node 22) a missing node fails the run instead. The end-to-end tests (`tests/e2e/`, marker `e2e`, opt-in like `image`) drive the real page in headless Chromium through Playwright against an in-process test-mode broker seeded by `tests/ui_world.py` (three rooms, one closed, four scripted agents, a Markdown-rich conversation): sign-in and connection, the header chips, Markdown and link safety, light and dark, the phone layout, the Inspector and Hold, the palette and @mentions, Mermaid diagrams (drawn on click, light and dark, a hostile diagram), closing and reopening a room, keyboard focus (including where it goes after a re-render, a kick or a sheet closes), and on a hosted broker the passkeys and the agent tokens. Every page fails its test on a console error, an uncaught page error or a CSP violation. Once per machine, `uv run playwright install chromium` downloads the browser into your user cache (add `--with-deps` on a bare Linux box for its system libraries); then:

```bash
uv run pytest -m e2e tests/e2e                     # add --headed or --slowmo 250 to watch
uv run playwright show-trace e2e-artifacts/<test>/context0-trace.zip   # after a failure
```

A failing test leaves a Playwright trace and a screenshot of each open page in `e2e-artifacts/<test>/` (ignored by git; `SWITCHBOARD_E2E_ARTIFACTS` moves it). Added stand-in agents close after their test; the four seeded agents remain until their world ends. With `-m e2e -n auto`, pytest assigns each small module to one worker and divides `test_web_ui.py` across three stable worker groups. On the eight-worker shared machine this reduced the peak from 9.7 GiB to 3.5 GiB; the run takes about 72 seconds instead of about 35 seconds. `uv run python docs/media/ui_shots.py` regenerates the 21 screenshots in `docs/media/ui/` from the same seeded world, plus an unclaimed hosted broker for the claim page, the passkey sign-in page and the Passkeys sheet, and a second one with test machines for the Machines sheet (`--out DIR` writes them elsewhere). CI's `frontend` job runs the e2e tests and `ui_shots.py` on `ubuntu-latest` and uploads the screenshots, plus any traces, as the `frontend-artifacts` artifact, pass or fail.

**Recording a change working.** For a change to something a person does in the web UI, the pull request's Verification carries a short captioned recording, made from the same seeded world: `uv run --group record python docs/media/ui_record.py <scenario> --out DIR` writes an MP4, a smaller GIF, and a sheet of its steps to check before posting. None of them is ever committed, to any branch, `design-assets` included: the MP4 is attached to the pull request through GitHub's own upload, which keeps it outside the repository. A scenario is a small file of clicks and captions; the [`record-verification`](.claude/skills/record-verification/SKILL.md) skill has the procedure and [docs/media/README.md](docs/media/README.md) how the script works. The `record` dependency group (`imageio-ffmpeg`, `pillow`) is only for this: `uv sync` doesn't install it, and CI never runs the script, only the unit tests of its timing (`tests/unit/test_ui_record.py`).

**Updating Mermaid** (the diagrams, [DESIGN.md §33](docs/DESIGN.md)) is a pull request of its own. Take `mermaid-<version>.tgz` from `registry.npmjs.org`, check it against `npm view mermaid@<version> dist.integrity`, and copy its `dist/mermaid.min.js` and `LICENSE`, unmodified, over the two files in `src/switchboard/web/static/vendor/mermaid/`. Then update their sha256 in `tests/unit/test_web_static_lint.py`, the version in DESIGN §33, `diagram.js` and the README, and run the e2e tests, which draw a hostile diagram.

**Coverage.** `uv run pytest --cov` adds line coverage of `src/switchboard` (settings in `pyproject.toml`, `[tool.coverage.*]`) and lists the missed lines of each file; add `--cov-report=html` for a browsable `htmlcov/`. It also measures the Python processes the tests start (the broker, CLI runs): coverage's `patch = ["subprocess"]` hands them its settings in `COVERAGE_PROCESS_CONFIG`, which `child_env()` in `tests/conftest.py` passes on. CI uploads each OS's data, and the `coverage` job combines Linux and macOS, prints the report and fails when the total drops below `COVERAGE_FLOOR` in `.github/workflows/test.yml`. That floor is a ratchet: raise it as coverage improves, never lower it to get a change through. Cover code with a test that checks what it does, not one that only runs it. `# pragma: no cover` is kept for code that can't run in CI (paths that need a real agent CLI, an OS CI doesn't run, guards for states the code never creates), and each one says why in the same comment. After each merge, the `badge` job in `.github/workflows/release.yml` takes the merged PR's shields.io endpoint file, `coverage.json`, from that PR's CI run and commits it to the orphan `badges` branch, which the coverage badge above reads. A PR that skipped the tests leaves the badge where it was.

**The container image** (`deploy/image/Dockerfile`, [docs/DEPLOY.md](docs/DEPLOY.md)) has tests of its own in `tests/image/` (marker `image`, opt-in, Docker and Playwright's Chromium needed). They start the image the way a platform does, behind Caddy terminating TLS with a certificate from its own CA, and check:
- that it runs as its unprivileged user and passes `/healthz` and Docker's health check;
- the claim link from `docker logs`, opened in Chromium through the proxy with a virtual authenticator: the claim, then a passkey sign-in, with no `docker exec` (issue #41);
- a sign-in link from `docker exec -t`, the Secure cookie, and the UI in Chromium over https and wss;
- that `docker stop` exits 0 and the data (the owner included) survives a restart;
- a root-owned disk (Render), and an fsGroup volume under the Kubernetes manifest's securityContext.

```bash
docker build -t switchboard:dev -f deploy/image/Dockerfile .
SWITCHBOARD_IMAGE=switchboard:dev uv run pytest -m image tests/image   # about 20 seconds; unset, it builds switchboard:test itself
```

The UI's screenshot lands in `e2e-artifacts/image/`. CI's `image` job builds the image for linux/amd64 on every PR that runs the tests (with the build cache), runs these, and uploads the screenshot as `image-artifacts`.
On Linux, the fixture waits for the Docker bridge and both container links to finish IPv6 address setup before opening Chromium. A proxy health check can pass earlier, while the later address change interrupts a browser request with `ERR_NETWORK_CHANGED`.

**Linux:** `docker compose -f sandbox/compose.yaml run --rm test` runs the same suite in a Debian 12 container (no network, non-root; pytest arguments pass through), and CI (`.github/workflows/test.yml`) runs it on `ubuntu-latest` and `macos-latest`. See [docs/SANDBOX.md §10](docs/SANDBOX.md#10-the-linux-test-run).

**CI** (issue #46).
- **Only on pull requests:** `.github/workflows/test.yml` runs on every PR, and by hand with `gh workflow run test.yml --ref <branch>`, never on `main`. `main` takes only PRs whose checks passed, so nothing re-runs the tests after a merge.
- **What runs:** the first job, `what changed` (`.github/scripts/ci_scope.py`), reads the PR's files. A docs-only PR (Markdown outside `src/` and `tests/`, images and video under `docs/`) and a release PR skip the tests and run only the tree scan (`tests/unit/test_tree_scan.py`). Any other PR runs all of it. It also fails a PR that edits CHANGELOG.md (see "The notes" below).
- **Security reports:** `.github/workflows/security.yml` uses the same scope for PRs and also runs after code merges to `main`. Its reports are artifacts, not code scanning alerts or a required check.
- **The check that counts:** `CI`, the last job, passes when `what changed` did and then either lint and every test job or the tree scan did. The ruleset on `main` requires it and `conventional PR title`, and refuses direct pushes, force pushes and deletion, with no exceptions for anyone. To merge as soon as the checks pass, run `gh pr merge --auto --squash`.
- **The trade-off:** each PR is tested against `main` as it was when its CI ran, so two PRs that pass separately can still clash once both are merged. The next PR's CI catches it.

**Releases.** A release is a pull request too (issue #46; before it, every merge was a release, #33).
- **PR titles** follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>)!: <subject>`, with the type one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` or `revert`. The `pr-title` check enforces it. PRs are squash-merged, so the title becomes the one commit on `main`, and the commits on a branch can say anything. A release PR's title is `release: vX.Y.Z`.
- **The bump:** a release is a minor version (0.6.x to 0.7.0) when anything since the last release is a `feat:` or a breaking change (`!` after the type, also a minor while we're below 1.0), and a patch otherwise, docs included.
- **The notes:** write them for users in the PR itself, in a new file, `changes/<name>.md`, named after the branch, under the CHANGELOG's headings ([changes/README.md](changes/README.md)). The next release gathers every file into `## X.Y.Z (date)` and the GitHub Release's notes, and deletes them. With no notes at all, the notes are the PRs' titles.
- **Never edit CHANGELOG.md in a PR.** Only a release writes it, and CI (`what changed`) fails a PR that does. In one shared section, notes conflicted between parallel PRs and a rebase could quietly file them under a release that was already out. To fix a release's notes after it's out, scope the title `(changelog)`.
- **Cutting a release:** run `python3 .github/scripts/release.py --open-pr` from any clean checkout. It works in a temporary worktree on a fresh branch from `origin/main`, never your checkout, and:
  - sets the version in `pyproject.toml`, `switchboard/__init__.py` and `uv.lock`;
  - gathers the notes in `changes/` into the CHANGELOG's new section, and deletes them;
  - moves any `uv tool install git+…@vX.Y.Z` pin in the README and `docs/INSTALL.md` (they now install `switchboard-chat` from PyPI, unpinned), and the `ghcr.io/amahpour/switchboard:X.Y.Z` pins in `docs/DEPLOY.md` and the examples in `deploy/`;
  - moves the `ref` of the plugin in both marketplace files (`.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`) to the new tag. The marketplaces serve the plugin of the latest release and not of `main`, so a plugin change reaches the people who installed it with a release, after the server it needs, and never with its own merge (#462, [DESIGN.md §49.5](docs/DESIGN.md#495-the-plugin-and-connect-an-agent-384)). It stops, and says which file, if one has no plugin pinned to a release tag.

  It then commits `release: vX.Y.Z` on `release/vX.Y.Z` and opens the PR, whose CI runs only the tree scan. It refuses while another release PR is open. Don't change the version, or a marketplace's `ref`, by hand. Agents cut releases when asked ([CLAUDE.md](CLAUDE.md)).
- **Publishing:** merging the release PR runs `.github/workflows/release.yml`, which runs no tests. It tags the merge commit `vX.Y.Z` and publishes the GitHub Release with the version's CHANGELOG section, then the image and the package on PyPI. A tag isn't covered by the ruleset, so GitHub's own token is enough. For about a minute after the merge the marketplaces name a tag that isn't there yet: an update in that minute keeps the plugin that is installed, and a later one installs the release's (Claude Code's next update; Codex's after the next change merges to `main`, or when it lists its plugins). There is nothing to do about it ([DESIGN.md §49.5](docs/DESIGN.md#495-the-plugin-and-connect-an-agent-384)).
- **The image:** after the release, the `publish-image` job (`.github/workflows/image.yml`) builds the new tag for linux/amd64 and linux/arm64. It pushes `ghcr.io/amahpour/switchboard:X.Y.Z`, plus `:latest` if it's the newest release, with a provenance attestation and an SBOM. To rebuild a release's image, for a base-image fix for example, run `gh workflow run image.yml -f version=X.Y.Z`. The package's very first push lands **private**, GitHub's default for a personal account's packages. Switch it to public once, by hand, in the package's settings (Danger Zone, Change visibility). GitHub has no API for that, and it can't be undone. To check without logging in, run `curl -s "https://ghcr.io/token?scope=repository:amahpour/switchboard:pull"`: a public package gets a token, and a private or missing one gets `DENIED`.

- **PyPI:** after the release, `build-dist` builds the sdist and the wheel from the new tag, checks them (`.github/scripts/check_dist.py`: the name and version, the web UI's files and the hook reply table in the wheel, nothing but the source in the sdist, and the wheel installing into a fresh environment and running `switchboard --version`), and attaches both to the GitHub Release. Then `publish-pypi` uploads them to PyPI as `switchboard-chat` with [trusted publishing](https://docs.pypi.org/trusted-publishers/): PyPI accepts an upload from this repo's `release.yml` in its `pypi` environment, so there's no token to store. CI runs the same check on every pull request (the lint job). To publish a release that failed to upload, re-run its failed job; a version that's already on PyPI can't be uploaded again, so a broken one is fixed by the next patch.

**Shards in CI.**
- **How CI splits it:** CI runs the default suite as three shards per OS, each on its own runner with xdist on that runner's cores. A hosted runner has only 3–4 cores, and more xdist workers than cores gains little, since each worker imports and collects the whole suite. So the run gets shorter by using more runners, not more workers.
- **How the shards are balanced:** [pytest-split](https://github.com/jerry-git/pytest-split) balances them by the per-test durations recorded in `tests/.test_durations` (`--splits 3 --group N --splitting-algorithm least_duration`). A test that isn't in the file counts as the average one.
- **Keeping the file current:** when tests are added or their times change a lot, regenerate it and commit it:

  ```bash
  uv run pytest -n auto --store-durations
  ```

- **Locally, nothing changes:** run the suite whole with `-n auto` (pytest-split does nothing without `--splits`). To run one CI shard, add `--splits 3 --group 2 --splitting-algorithm least_duration`.
- **Sharing a machine:** when several agents (or people) work on one machine, the suites run one at a time. `-n auto` starts a worker on every core, and every worker starts brokers and scripted agents; the e2e tests add a Chromium each. Three such runs at once pushed a 30 GB machine into swap until it froze (2026-10-12). Take a lock and cap the workers:

  ```sh
  PYTEST_XDIST_AUTO_NUM_WORKERS=8 flock "${XDG_RUNTIME_DIR:-/tmp}/switchboard-suite.lock" uv run pytest -q -n auto
  ```

  `flock` waits for the run that holds the lock, and the variable makes `-n auto` mean eight workers. On Linux, `systemd-run --user --scope -p MemoryMax=12G -p MemorySwapMax=0 -- <the command>` also caps the run's memory, so a run that grows past it is killed and fails instead of taking the machine down. Before the e2e world lifecycle and scheduling fix, eight workers peaked near 9.7 GiB; with per-test cleanup and three groups for the large module, 3.5 GiB. The existing 12 GiB cap leaves room for other suites. Check that the cap took (`cat /proc/<a test process's pid>/cgroup` names the scope it runs in): a `uv` installed as a snap moves the command into a scope of its own, `snap.astral-uv.uv-<id>.scope`, where that limit doesn't reach. There, cap the scope it landed in once the run has started: `systemctl --user set-property --runtime <that scope> MemoryMax=12G MemorySwapMax=0`. An agent that starts other agents tells each of them the exact command.

### Live tests (real agent CLIs, opt-in)

`tests/live/` drives the real Claude Code, Codex, OpenCode V2, Devin and Cursor CLIs over HTTPS ([DESIGN.md §12.4](docs/DESIGN.md) has the design). They are marked `live`, never run by a plain `pytest` (each module skips itself with the line that says how to run it) and never in CI. Each starts a throwaway broker in a temp home, makes an agent token through the web API, and runs one CLI in a private tmux server with the plugin or config from your checkout (OpenCode uses a private standalone server, below). It then plays the person through the web API: the agent joins and says something; an @mention wakes it while idle; one arrives mid-task and is delivered after its next tool call; a subagent's tool calls take nothing meant for the session; quitting shows it offline and resuming brings it back; a killed Devin shows offline; a revoked token ends it.

```bash
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude.py -s -q   # or codex, devin, cursor
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude_signin.py -s -q   # Claude Code signed in through the browser
SWITCHBOARD_LIVE=claude,codex,opencode,devin,cursor uv run pytest -m live tests/live -s -q    # all of them, one after the other
```

- **What you need:** the CLI on `PATH`, logged in (`claude`, `codex login`, `devin auth login`, `agent login`), `tmux` and `curl`. A harness whose CLI or login is missing is skipped with the reason.
- **What they cost:** the cheapest model each account has (Claude `haiku`, Codex `gpt-6-luna`, both at low effort; Devin `swe-1-6-slow`; Cursor `auto`), about a dozen model turns per harness. A run takes 25 to 50 s for Claude Code, about 40 s for Codex (about 0.4 million tokens, nearly all cached input), about a minute for Cursor and about 3 minutes for Devin (it waits out the 130 s a killed Devin takes to show offline; the free plan's quota fell by under 1 percentage point a run). Each ends with a `LIVE RESULTS` block: what each scenario found, and one line of what the run spent, read from the CLI's own record (Claude Code's transcript, Codex's rollout, Devin's quota banner). Cursor's free account may be out of quota: its first test needs no model, and the rest are skipped, with the reason, until a one-word call works.
- **The sign-in run** (`test_live_claude_signin.py`, the same `claude` switch, #488) types no token: Claude Code signs the plugin's server in through the browser (`/mcp`, Authenticate), a headless Chromium signed in as the throwaway hosted broker's admin approves it on the consent card, and the scenarios then run on that sign-in: join, an idle wake through the listener key, the key shown to open no tool and no other session, quit, a resume woken before its first turn, and a revoked sign-in. It needs Playwright's Chromium (`uv run playwright install chromium`, as the e2e tests do) and skips with that reason without it. Claude Code runs with a throwaway `CLAUDE_CONFIG_DIR` that holds a copy of the account's login only (0600, deleted with the run), so nothing in the real `~/.claude` changes.
- **What they touch:** a temp directory per run, which they remove. Claude Code, Devin and Cursor use the real home for their logins only: Claude Code writes its transcripts and a `~/.claude.json` entry there (the run deletes its transcripts; `~/.claude.json` is reported, not failed). Codex gets a temp `CODEX_HOME` with a **copy** of `~/.codex/auth.json` (mode 0600, deleted at the end, never printed); Codex may rotate a refresh token in the copy, so run Codex's live test only when you can log in again. After a run the md5s of the real `~/.claude/settings.json`, `~/.codex/{config.toml,hooks.json}`, `~/.cursor/{mcp,hooks}.json` and `~/.config/devin/*.json` must be what they were, or the run fails. No approval is ever given: a prompt that appears is declined with Esc.
- **Trying a plugin change:** `SWITCHBOARD_LIVE_CLAUDE_PLUGIN`, `SWITCHBOARD_LIVE_CODEX_PLUGIN` and `SWITCHBOARD_LIVE_CURSOR_PLUGIN` name a plugin folder to use instead of the checkout's, for a change that isn't a plugin version yet, or to see a scenario fail against a plugin with a hook taken out. `SWITCHBOARD_LIVE_KEEP=1` keeps the run's temp directory (the broker's log and database; not the Codex login).
- **A failure** prints the CLI's screen, the broker's log, Members, the engine's last events and the run's processes. Every wait has a deadline and none sleeps to mean "by now". A live test that fails sometimes is a bug in the test or in the product (the first is fixed, the second gets an issue): never re-run it until it passes.
- **Run them** when a change touches `plugins/`, `adapters/https.py`, the hook replies or the engine's delivery to a harness, and say in the pull request what they printed. `tests/unit/test_live_harness.py` runs on every run and checks everything about them that needs no model.

**OpenCode V2** (#513) has a separate private-server test:

```bash
SWITCHBOARD_LIVE=opencode uv run pytest -m live tests/live/test_live_opencode.py -s -q
```

It needs `opencode` (tested on 2.1.4) and `OPENAI_API_KEY`, uses `openai/gpt-5.4-nano`, and prints `LIVE RESULTS`. It runs `opencode run --standalone` with a temporary HOME, all XDG paths, `OPENCODE_CONFIG_DIR`, project and `OPENCODE_CONFIG_CONTENT`. It never reads or writes the real OpenCode configuration or database, starts no background service, and performs no sign-in. Only the provider key is inherited through the allowlisted environment. A test-only local driver holds the standalone server open while a second real session joins, talks and is woken; it creates a private permission request and never answers it. The shipped plugin supplies all broker status and wake behavior. A plain suite skips this module, as it does the other `live` modules.

### Evals (real agents, graded from the database, opt-in)

`tests/evals/` asks what the live tests don't: not whether the plumbing works, but what a model does with the room's rules. A scripted person plays against three real Claude Code agents in a throwaway room ([DESIGN.md §12.7](docs/DESIGN.md)), each run is graded from the broker's database, and a scenario repeats k times because agents aren't deterministic. Use it to see whether a change to the text agents read (`ROOM_RULES`, the join text, a room's own rules) or to who a message wakes makes a difference, before and after. It never runs in CI or by default (the module skips itself with the line that says how to run it), and a harness error (a timeout, a crash) is counted apart from a failed check.

```bash
# the first slice: three scenarios, Claude Code only (alpha, bravo and charlie in #build)
SWITCHBOARD_EVAL=claude flock "${XDG_RUNTIME_DIR:-/tmp}/switchboard-suite.lock" \
  uv run python tests/evals/run_evals.py run --arm baseline --k 5
uv run python tests/evals/run_evals.py list                      # the scenarios and their checks
SWITCHBOARD_EVAL=claude uv run pytest -m eval tests/evals -s -q  # one real trial, as a smoke test
```

- **What you need:** `claude` logged in and `tmux` on `PATH`, as for the live tests. Real CLIs in tmux are heavy: run one eval at a time, under the same lock as the suites ("Sharing a machine").
- **What it costs:** Measured on 2026-10-22 (Claude Code 2.1.307, `haiku` at low effort, tokens priced at the published rates): a trial takes about 32 s (12 to 21 s from the question to a settled room; the rest is three CLIs starting and joining) and costs about 1.3 cents, 0.54 to 0.77 million tokens, nearly all cache reads, of which 0.2 to 0.45 million come after the question. Twenty-five trials (the first experiment, #480) took 13 minutes and 32 cents. At the published rates `sonnet` costs twenty times as much a token. Each run is capped: a trial stops at `--token-cap` tokens (3 million by default, all of an agent's tokens, cache reads included) and the whole run at `--max-cost` dollars (1.00 by default), and the room's wake budget and loop guard are on. The run prints each trial as it ends and writes `tests/evals/_results/<arm>-<time>.json`, which git ignores; the file has the cost.
- **What it touches:** what the live tests do: a temp directory per trial, the real home for Claude Code's login only, transcripts deleted with the trial, and `~/.claude/settings.json` checked before and after (a change stops the run). No approval is ever given: a prompt that appears is declined with Esc and counted.
- **Try a change:** run the baseline **twice** (the spread between two runs of the same thing is the noise a change has to beat), then the same command with the change on its own arm. The room's own rules (#105) change what agents read without touching the code: `--rules "When nobody is named, only the agent whose name sorts first answers; the others pass()."` or `--rules-file`. For a change in the code or a plugin, check out that change and run the same command.

  ```bash
  uv run python tests/evals/run_evals.py compare tests/evals/_results/baseline-1-<time>.json \
    tests/evals/_results/first-answers-<time>.json --repeat tests/evals/_results/baseline-2-<time>.json
  ```

  `compare` prints each check as `4/5 -> 5/5` (of the trials that were graded) with the harness errors beside them, then the change in tokens after the question, cost, wakes, wakes that ended in a `pass()` and posts, each against the spread of the two baseline runs: it says **REAL** only for a change larger than that spread. Without `--repeat` nothing is called real. Iterate on the cheapest model (the default `--model haiku`), and confirm a change that matters on the model people use (`--model sonnet`, twenty times the price a token).
- **Add a scenario:** a file in `tests/evals/scenarios/<name>.toml` with the room, the `agents`, the person's `[[steps]]` (`say = "..."`) and `[[checks]]`: each has an `id` (its name in the results), a `grader` from `tests/evals/evalkit/graders.py` and that grader's arguments. A scenario that names a grader, argument or agent that doesn't exist is refused when it is read (`run_evals.py list` reads them all). Then add the scripted rooms that fail and pass each of its checks to `ROOMS` in `tests/integration/test_evals_graders.py`: the regular suite fails if a check has no pair. A new kind of check is a function in `graders.py` that takes the run record and returns a `Result`; it reads the store, never what an agent said, and no model judges.
- **What it doesn't measure yet:** a trial ends when the room has settled: every agent idle, nothing addressed to an agent waiting, nothing moving for 8 seconds. Chatter that addresses nobody waits in the engine for its hold (`unaddressed_hold_s`, 270 s, [§8.2](docs/DESIGN.md)) and is not waited for, so the wakes it causes later are not counted. Codex and the other harnesses, nightly runs and a judge are later slices (#480, #119).
