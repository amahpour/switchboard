# Contributing

The project was built in milestones: Milestone 0 tested what each harness can do, and Milestones 1–7 built the broker, the web UI, the CLI, the agent MCP server, the hooks, `switchboard install` / `uninstall` (`install` and the per-session MCP server and hook script are retired since 0.38.0, #385: agents connect over HTTPS), the delivery engine, per-harness delivery and `switchboard report`; Milestone 8 added remote members over SSH (retired in 0.38.0, #385: agents connect over HTTPS now). The milestones and their acceptance criteria are in [DESIGN.md §13](docs/DESIGN.md#13-milestones-and-acceptance-criteria), the Milestone 0 results in [docs/FINDINGS.md](docs/FINDINGS.md), and the M7 live rehearsal (Claude, Codex and Devin together in one room) in [docs/M7-REPORT.md](docs/M7-REPORT.md). Each change adds its release notes as a file in [`changes/`](changes/README.md), and updates the README or the docs it touches. A pull request that changes anything a person sees shows it: screenshots in its description, before and after, made with `docs/media/ui_shots.py` or `docs/media/cli_shots.py` (see [CLAUDE.md](CLAUDE.md) for where the images go).

**Changes come as pull requests,** from a branch here or from a fork, and the maintainer reviews and merges each one. If a coding agent writes yours, point it at [CLAUDE.md](CLAUDE.md): how a change lands, where the code and the tests live, and what has to be right. The same file is for people.

**Reviews follow the repository's own rules.** `REVIEW.md` files at the root and in `plugins/`, `deploy/joinly/`, `src/switchboard/web/` and `tests/` say what a review flags and what it skips, with the bug each line comes from. Reviewers, agents on a [review board](docs/guide/review-board.md) included, read the ones nearest the changed files, from the default branch, so a pull request cannot change the rules it is reviewed under. Each finding carries a level: only an Important one blocks the merge, and after two rounds only Important ones are raised, after one for a pull request of only tests or tooling (the root `REVIEW.md`, "Levels"). If a review keeps catching or missing something, add a line to the nearest one.

## Development

Development needs uv 0.7.13 or newer: `pyproject.toml` sets `[tool.uv] required-version = ">=0.7.13"`. CI and the Linux test container stay on 0.7.13 with `--frozen`, so a newer uv that would change `uv.lock` fails CI instead of slipping through (uv 0.12 re-locks the current lock unchanged).

**Dev mode (like `pip install -e`).** Either run from the checkout with `uv run switchboard start` (the project `.venv` from `uv sync` is already editable), or make the global command point at the checkout with `uv tool install --editable .`. Then:
- web UI changes (`src/switchboard/web/static/`): just refresh the browser, since the files are served from disk with `no-cache`;
- Python changes: restart the broker, `switchboard stop && switchboard start` (only one broker runs per home, so stop an installed one first);
- An agent connects over HTTPS with an agent token and switchboard's plugin, so nothing of this checkout runs on its side. Run a regular install (`uv tool install --reinstall .`) for a broker you leave running, so an agent editing this repo can't change it.

`uv sync` (project-local `.venv`), then `uv run pytest -q -n auto` runs the unit and integration tests in parallel on every core (about 2,500 tests in about 3 minutes, or about 9 without `-n auto`, including a 200-seed property test of the delivery rules; the integration tests start in-process brokers and scripted agents that call them over HTTPS, as an agent does). A test that leaves behind an object whose `__del__` raises — a resource forgotten to close, such as the leaked asyncio transport in #276 — fails too, in the test that leaked it: `pyproject.toml`'s `filterwarnings` turns `PytestUnraisableExceptionWarning` into an error, and `tests/conftest.py`'s `fail_on_unraisable_exception` (autouse) collects generations 0 and 1 after every test so the object is reclaimed there rather than in whichever later test the collector happens to next run in (issue #277; a full `gc.collect()` there instead measured at ~0.25s per test, about 13 minutes over this suite, against ~1ms for generations 0 and 1 alone, since gen 2 holds every object the process has ever promoted and a leaked object hasn't survived a collection yet). Strict timing checks are marked `perf` (`uv run pytest -m perf`). **Lint and static analysis:** `uv run python scripts/lint.py` runs Ruff, mypy, ESLint, ShellCheck, actionlint and, for the Helm chart in `deploy/helm/`, `helm lint --strict` and the chart's tests (`tests/unit/test_deploy_helm.py`, which compare its render with `deploy/kubernetes/`). Add `--fix` to format the Python tree and apply safe ESLint fixes. Node 22 is needed; ESLint's npm dependencies are locked in `scripts/eslint/`, and the script downloads checksum-verified ShellCheck, actionlint and Helm into ignored `.lint-tools/`. A plain `pytest` skips the chart's render tests where it finds no helm (`SWITCHBOARD_HELM`, or the one lint fetched); lint runs them with `SWITCHBOARD_REQUIRE_HELM=1`, so CI can't skip them. No Ruff or mypy findings are pinned (there is no `.lint-baseline.json`); new Python findings fail. The formatter checks the whole Python tree. CI runs the same command in a parallel `lint` job for code PRs.

**Cloud agents.** A Cursor Cloud Agent can prepare its machine with `.cursor/environment.json`, which runs `.cursor/install.sh` from the repository root: uv 0.7.13 and CPython 3.13 as CI pins them, Node 22.23.5 (CI's Node major, at a patch the script pins for its checksum), each download checked against its pinned SHA-256, and `uv sync --frozen`. Cursor uses the file only when no saved environment of yours or your team's matches the repository first, and a saved environment reads it only when its **environment.json location** points at this repository's file ([Cursor's resolution order](https://cursor.com/docs/cloud-agent/setup#environment-resolution-order)). A new saved environment starts with the location set to none, so pick this repository as its location (or let a single-repository agent start make one, which points at the committed file), then wait for a Build to succeed: agents start from the newest successful Build, and a failed one leaves the old one active. The script runs for every Build, on a fresh disk or one an earlier Build prepared, so every step checks before it acts; `tests/unit/test_cursor_environment.py` fails when CI's pins move and the script's don't, or when a download isn't pinned and checksummed. The e2e tests' Chromium isn't installed (`playwright install --with-deps` needs root): a cloud agent runs lint and the default suite, and CI runs the rest.

**The plugins' scripts** exist twice for Claude Code: `sh` and `curl` for Linux and macOS (`plugins/claude/bin/listen`, `session`), and PowerShell for Windows (`plugins/claude/bin/windows/`, DESIGN.md §49.5). The tests that run them (`tests/integration/test_agent_plugins.py`) run each against both, the PowerShell ones under `pwsh` (PowerShell 7) when it is on PATH; without it they are skipped, but with `SWITCHBOARD_REQUIRE_PWSH=1` (set in CI, whose runners have it) a missing `pwsh` fails the run instead. A change to a PowerShell script is also run under Windows PowerShell 5.1 on a Windows machine, which no CI job has: keep the files ASCII and free of PowerShell 7-only syntax (a test checks both). The helper that makes Claude Code's listener key (`plugins/claude/bin/headers`, DESIGN.md §49.11) has its twin too: Claude Code runs a `headersHelper` with `cmd.exe` on Windows, which finds `bin/headers.cmd`, which starts `bin/windows/headers.ps1`. Its tests (`tests/integration/test_claude_plugin_signin.py`) run the helper and the listener's and session script's key use once for each implementation, and `tests/integration/test_claude_plugin_windows.py` checks what only Windows does (the access list that stands in for mode 0600, the walk to Claude Code's pid) in the source, so a change to either is also run on Windows by hand.

**Security reports:** `uv run python scripts/security_scan.py` runs Bandit on Python, pip-audit on every pinned package exported from `uv.lock`, an OSV query for the vendored Mermaid version, and zizmor on workflows. Findings print a count and do not fail the command; scanner errors do fail it. `--out DIR` keeps the JSON/SARIF files. The parallel `security.yml` workflow adds CodeQL (Python, JavaScript and Actions), Trivy on a freshly built image, and gitleaks on the full Git history; it redacts secrets and removes author details from the saved report. Open the run's artifacts to read the full reports. These jobs run on code PRs and `main`; docs-only and release changes skip them. They do not upload to code scanning and are not in the required `CI` aggregate. Fix a finding in its own PR, or document why it is a false positive; there is no suppression baseline or severity gate yet (DESIGN.md §36).

**The web UI** has three layers of tests. The node tests (`tests/unit/test_web_markdown.py`, `test_web_app_behavior.py`, `test_web_diagram.py`) run `md.js`, `app.js` and `diagram.js` in node against a fake DOM, in the default suite; without `node` on PATH they are skipped, but with `SWITCHBOARD_REQUIRE_NODE=1` (set in CI, which installs node 22) a missing node fails the run instead. The end-to-end tests (`tests/e2e/`, marker `e2e`, opt-in like `image`) drive the real page in headless Chromium through Playwright against an in-process test-mode broker seeded by `tests/ui_world.py` (three rooms, one closed, four scripted agents, a Markdown-rich conversation): sign-in and connection, the header chips, Markdown and link safety, light and dark, the phone layout, the Inspector and Hold, the palette and @mentions, Mermaid diagrams (drawn on click, light and dark, a hostile diagram), closing and reopening a room, keyboard focus (including where it goes after a re-render, a kick or a sheet closes), and on a hosted broker the passkeys and the agent tokens. Every page fails its test on a console error, an uncaught page error or a CSP violation. Once per machine, `uv run playwright install chromium` downloads the browser into your user cache (add `--with-deps` on a bare Linux box for its system libraries); then:

```bash
uv run pytest -m e2e tests/e2e                     # add --headed or --slowmo 250 to watch
uv run playwright show-trace e2e-artifacts/<test>/context0-trace.zip   # after a failure
```

A failing test leaves a Playwright trace and a screenshot of each open page in `e2e-artifacts/<test>/` (ignored by git; `SWITCHBOARD_E2E_ARTIFACTS` moves it). Added stand-in agents close after their test; the four seeded agents remain until their world ends. With `-m e2e -n auto`, pytest assigns each small module to one worker and divides `test_web_ui.py` across three stable worker groups. On the eight-worker shared machine this reduced the peak from 9.7 GiB to 3.5 GiB; the run takes about 72 seconds instead of about 35 seconds. `uv run python docs/media/ui_shots.py` regenerates the 21 screenshots in `docs/media/ui/` from the same seeded world, plus an unclaimed hosted broker for the claim page, the passkey sign-in page and the Passkeys sheet, and a second one with test machines for the Machines sheet (`--out DIR` writes them elsewhere). CI's `frontend` job runs the e2e tests and `ui_shots.py` on `ubuntu-latest` and uploads the screenshots, plus any traces, as the `frontend-artifacts` artifact, pass or fail: a failed test's, and with `ui_shots.py --traces DIR` a failed shot's (`shot-traces/<shot>-<n>.zip`; open one with `uv run playwright show-trace <file>`, #1001). The layout sweep (`tests/e2e/test_layout_sweep.py`, #995) runs in a job of its own, `layout`, four workers at a time, because its 105 cases would take the `frontend` job past its timeout.

**Recording a change working.** For a change to something a person does in the web UI, the pull request's Verification carries a short captioned recording, made from the same seeded world: `uv run --group record python docs/media/ui_record.py <scenario> --out DIR` writes an MP4, a smaller GIF, and a sheet of its steps to check before posting. None of them is ever committed, to any branch, `design-assets` included: the MP4 is attached to the pull request through GitHub's own upload, which keeps it outside the repository. A scenario is a small file of clicks and captions; the [`record-verification`](.claude/skills/record-verification/SKILL.md) skill has the procedure and [docs/media/README.md](docs/media/README.md) how the script works. The `record` dependency group (`imageio-ffmpeg`, `pillow`) is only for this: `uv sync` doesn't install it, and CI never runs the script, only the unit tests of its capture backend and timing (`tests/unit/test_ui_record.py`). Viewport screenshots include native full screen and share the captions' clock.

**The whiteboard bundle** (`src/switchboard/web/static/vendor/board/`, [DESIGN.md §56.8](docs/DESIGN.md)) is built from `scripts/board` and never edited by hand. After a change to `scripts/board/frame.jsx`, `build.mjs`, the lockfile or `board-rules.js`, run `scripts/board/check.sh --write` (Node 22; it runs `npm ci --ignore-scripts` and rebuilds), commit every file it changes (renamed chunks included; chunks it no longer writes are removed), and update the hashes in `tests/unit/test_web_static_lint.py`. `scripts/board/check.sh` alone rebuilds into a temporary folder and fails on any difference; CI runs it in the `lint` job.

**Updating Mermaid** (the diagrams, [DESIGN.md §33](docs/DESIGN.md)) is a pull request of its own. Take `mermaid-<version>.tgz` from `registry.npmjs.org`, check it against `npm view mermaid@<version> dist.integrity`, and copy its `dist/mermaid.min.js` and `LICENSE`, unmodified, over the two files in `src/switchboard/web/static/vendor/mermaid/`. Then update their sha256 in `tests/unit/test_web_static_lint.py`, the version in DESIGN §33, `diagram.js` and the README, and run the e2e tests, which draw a hostile diagram.

**Coverage.** `uv run pytest --cov` adds line coverage of `src/switchboard` (settings in `pyproject.toml`, `[tool.coverage.*]`) and lists the missed lines of each file; add `--cov-report=html` for a browsable `htmlcov/`. It also measures the Python processes the tests start (the broker, CLI runs): coverage's `patch = ["subprocess"]` hands them its settings in `COVERAGE_PROCESS_CONFIG`, which `child_env()` in `tests/conftest.py` passes on. CI uploads each OS's data, and the `coverage` job combines Linux and macOS, prints the report and fails when the total drops below `COVERAGE_FLOOR` in `.github/workflows/test.yml`. That floor is a ratchet: raise it as coverage improves, never lower it to get a change through. Cover code with a test that checks what it does, not one that only runs it. `# pragma: no cover` is kept for code that can't run in CI (paths that need a real agent CLI, an OS CI doesn't run, guards for states the code never creates), and each one says why in the same comment. After each merge, the `badge` job in `.github/workflows/release.yml` takes the merged PR's shields.io endpoint file, `coverage.json`, from that PR's CI run and commits it to the orphan `badges` branch, which the coverage badge above reads. A PR that skipped the tests leaves the badge where it was.

**The container image** (`deploy/image/Dockerfile`, [docs/DEPLOY.md](docs/DEPLOY.md)) has tests of its own in `tests/image/` (marker `image`, opt-in, Docker and Playwright's Chromium needed). They start the image the way a platform does, behind Caddy terminating TLS with a certificate from its own CA, and check:
- that it runs as its unprivileged user and passes `/healthz` and Docker's health check;
- the claim link from `docker logs`, opened in Chromium through the proxy with a virtual authenticator: the claim, then a passkey sign-in, with no `docker exec` (issue #41);
- a sign-in link from `docker exec -t`, the Secure cookie, and the UI in Chromium over https and wss;
- that `docker stop` exits 0 and the data (the owner included) survives a restart;
- a root-owned disk (Render), and an fsGroup volume under the Kubernetes manifest's securityContext.

```bash
docker build -t switchboard:dev -f deploy/image/Dockerfile .
SWITCHBOARD_IMAGE=switchboard:dev uv run pytest -m image tests/image   # about 20 seconds; unset, it builds switchboard:test itself
```

The same image job also checks Litestream recovery against MinIO (#689): an old schema is replicated,
then migrated by the broker, written and checkpointed, and recovered from S3 after losing the volume.
CI provisions the pinned Litestream image and builds `switchboard:litestream-minio` from pinned
upstream server/client commits and their `go.sum` files (`tests/image/Dockerfile.minio`), since the
public MinIO images were withdrawn. Local runs use cached images only and skip this drill if either
image is absent; they never pull. The process/socket drill also runs 20 times alone and once with xdist.

The UI's screenshot lands in `e2e-artifacts/image/`. CI's `image` job builds the image for linux/amd64 on every PR that runs the tests (with the build cache), runs these, and uploads the screenshot as `image-artifacts`.
On Linux, the fixture waits for the Docker bridge and both container links to finish IPv6 address setup before opening Chromium. A proxy health check can pass earlier, while the later address change interrupts a browser request with `ERR_NETWORK_CHANGED`.

**Linux:** `docker compose -f sandbox/compose.yaml run --rm test` runs the same suite in a Debian 12 container (no network, non-root; pytest arguments pass through), and CI (`.github/workflows/test.yml`) runs it on `ubuntu-latest` and `macos-latest`. See [docs/SANDBOX.md §10](docs/SANDBOX.md#10-the-linux-test-run).

**CI** (issue #46).
- **Only on pull requests:** `.github/workflows/test.yml` runs on every PR, and by hand with `gh workflow run test.yml --ref <branch>`, never on `main`. `main` takes only PRs whose checks passed, so nothing re-runs the tests after a merge. A manual run fetches `origin/main` and the full history before pytest so the plugin-version check compares the branch with its fork point from main; the required-base guard still fails if that base is unavailable.
- **What runs:** the first job, `what changed` (`.github/scripts/ci_scope.py`), reads the PR's files. A docs-only PR (Markdown outside `src/` and `tests/`, images and video under `docs/`) skips the tests and runs only the tree scan (`tests/unit/test_tree_scan.py`). Any other PR runs all of it, a release PR too: its tests run on the merge commit, which is `main` as the release will ship it, so two PRs that each passed alone are tested together before they ship (#970). Every PR, those included, builds the documentation site (`docs site`, below). It fails a release PR whose plugin manifests (`PLUGIN_MANIFESTS` in `release.py`) don't all carry the title's version, at once and before the tests (#901). It also fails a PR that edits CHANGELOG.md (see "The notes" below).
- **Security reports:** `.github/workflows/security.yml` uses the same scope for PRs and also runs after code merges to `main`. Its reports are artifacts, not code scanning alerts or a required check.
- **The check that counts:** `CI`, the last job, passes when `what changed` and `docs site` did and then either lint and every test job or the tree scan did. The ruleset on `main` requires it and `conventional PR title`, and refuses direct pushes, force pushes and deletion, with no exceptions for anyone. To merge as soon as the checks pass, run `gh pr merge --auto --squash`.
- **Downloads are cached** (#667): one outage of GitHub's release downloads must not turn every check red. Each job gets uv 0.7.13 and CPython 3.13 from the local action `.github/actions/setup-uv-python`, which keeps the managed Python in `actions/cache`, keyed on the OS, the CPU, the uv version and the Python series; on a hit it installs offline, so nothing is fetched from `astral-sh/python-build-standalone`. The `lint` job caches `.lint-tools/` the same way, keyed on `hashFiles('scripts/lint.py')`, the file that pins each tool's version and sha256. `scripts/lint.py` checks a restored archive against that sha256 exactly as it checks a download and takes the binary out of it every run, so a cached tool is no looser than a fresh one. A download that still fails (a GitHub 5xx, say) says "download failed" and that it is not a test or lint finding. Caches are written by `pull_request` runs, which GitHub scopes to the PR's own ref, and no workflow uses `pull_request_target`, so a fork's PR can't poison one that `main` reads. A PR's first run is cold, and a job that fails before it finishes saves nothing; its later pushes are warm. Pin every action in `.github/actions/` by full commit SHA like the workflows.
- **The trade-off:** each PR is tested against `main` as it was when its CI ran, so two PRs that pass separately can still clash once both are merged. The next PR's CI catches it.

**Docs and the site** (issue #586). The Markdown in `docs/` is the documentation and the site, https://amahpour.github.io/switchboard/, both: [Zensical](https://zensical.org) builds the one from the other (`zensical.toml`), so nothing is written twice.
- **A guide per feature** lives in `docs/guide/` (meetings, code review on a board, attachments): how it works, how to set it up, a walkthrough with pictures, what agents see, safety, limits, troubleshooting and a reference. A change to a feature updates its guide in the same PR, and a new feature gets one. `docs/USAGE.md` keeps a short summary of each and links to it.
- **Preview it:** `uv run --group docs zensical serve` serves the site on `localhost:8000` and rebuilds as you edit. `uv run --group docs zensical build --strict` builds it the way CI does. The `docs` group is not part of the regular setup.
- **Two rules,** checked by `tests/unit/test_docs_site.py`: a page under `docs/` is in `zensical.toml`'s `nav` or its `exclude_docs`, and a relative link never leaves `docs/`. GitHub follows `../SECURITY.md`, but the site serves `docs/` alone, so a link to anything outside it (README, SECURITY.md, a source file) is an absolute URL, `https://github.com/amahpour/switchboard/blob/main/SECURITY.md`.
- **In CI:** the `docs site` job builds the site with `--strict` on every PR, docs-only included, so a broken link or anchor fails `CI`, and runs those two tests. After the merge, `.github/workflows/docs.yml` builds it again and publishes it to GitHub Pages, so the site follows `main` within minutes. `gh workflow run docs.yml` publishes it again by hand.
- **Pictures** a guide uses live in `docs/media/ui/` and are made by `docs/media/ui_shots.py` from the seeded test world (`--only <set>` for one set), like the README's: test data only, a few small PNGs.

**Releases.** A release is a pull request too (issue #46; before it, every merge was a release, #33).
- **PR titles** follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>)!: <subject>`, with the type one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` or `revert`. The `pr-title` check enforces it. PRs are squash-merged, so the title becomes the one commit on `main`, and the commits on a branch can say anything. A release PR's title is `release: vX.Y.Z`.
- **The bump:** a release is a minor version (0.6.x to 0.7.0) when anything since the last release is a `feat:` or a breaking change (`!` after the type, also a minor while we're below 1.0), and a patch otherwise, docs included. From 1.0 a breaking change (`!`, or `BREAKING CHANGE` in the body) is a major (1.4.2 to 2.0.0). Below 1.0 the commits can never give a major, so the first one, 1.0.0, is cut on purpose: `python3 .github/scripts/release.py --open-pr --major` makes the release the next major (0.58.x to 1.0.0, 1.x to 2.0.0) whatever the commits say. Only the maintainer's explicit ask for that version runs it; `--major` works with `--open-pr` alone, the PR's title is still `release: vX.Y.Z`, and its body says it is a deliberate major.
- **Plugin compatibility is the major version (#850).** Any plugin works with any server of the same major version. A change needs that major when it changes the listen protocol: its endpoint, a header an older server reads, or the meaning of a header or a status; or when it removes or renames a tool, an action or a required parameter. A new optional header that an older server ignores is a minor addition, when the plugin still works without it; list it in `ADDITIVE_HEADERS` in `tests/integration/test_plugin_server_compat.py`. A skill that names a tool, an action or a parameter added after the major's first release fails that test, unless the skill says what to do on an older server and the name is in `FALLBACKS` there (#954). A minor release only adds, so within a major the order of updating the server and the plugin does not matter. The server warns a session when its plugin's major differs, or the version is unknown ([DESIGN.md §49.13](docs/DESIGN.md#4913-which-plugin-a-session-runs-789-850)); it does not warn for a different minor or patch. The maintainer's ask is still what cuts the major (`--major`, above).
- **The notes:** write them for users in the PR itself, in a new file, `changes/<name>.md`, named after the branch, under the CHANGELOG's headings ([changes/README.md](changes/README.md)). The next release gathers every file into `## X.Y.Z (date)` and the GitHub Release's notes, and deletes them. With no notes at all, the notes are the PRs' titles.
- **Never edit CHANGELOG.md in a PR.** Only a release writes it, and CI (`what changed`) fails a PR that does. In one shared section, notes conflicted between parallel PRs and a rebase could quietly file them under a release that was already out. To fix a release's notes after it's out, scope the title `(changelog)`.
- **Cutting a release:** run `python3 .github/scripts/release.py --open-pr` from a checkout of a fresh `origin/main` (`git fetch origin`, then `git worktree add <dir> origin/main`). It runs only as main's own copy of the script and stops otherwise: which files a release stamps is written in the script, and v1.11.0, cut with an older copy, left Devin's and OpenCode's plugins at 1.10.0. It works in a temporary worktree on a fresh branch from `origin/main`, never your checkout, and:
  - sets the version in `pyproject.toml`, `switchboard/__init__.py` and `uv.lock`;
  - gathers the notes in `changes/` into the CHANGELOG's new section, and deletes them;
  - moves any `uv tool install git+…@vX.Y.Z` pin in the README and `docs/INSTALL.md` (they now install `switchboard-chat` from PyPI, unpinned), and the `ghcr.io/amahpour/switchboard:X.Y.Z` pins in `docs/DEPLOY.md`, the examples in `deploy/` and the relay's Compose files in the Claude Code and Codex plugins (`plugins/claude/meeting/compose.yaml` and `plugins/codex/meeting/compose.yaml`, #623), and sets `appVersion` in the Helm chart (`deploy/helm/switchboard/Chart.yaml`), the image tag the chart installs (#608);
  - moves the `ref` of the plugin in both marketplace files (`.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`) to the new tag. The marketplaces serve the plugin of the latest release and not of `main`, so a plugin change reaches the people who installed it with a release, after the server it needs, and never with its own merge (#462, [DESIGN.md §49.5](docs/DESIGN.md#495-the-plugin-and-connect-an-agent-384)). It stops, and says which file, if one has no plugin pinned to a release tag.
  - sets the `version` of every plugin manifest (`plugins/claude/.claude-plugin/plugin.json`, `plugins/codex/.codex-plugin/plugin.json`, `plugins/cursor/.cursor-plugin/plugin.json`, `plugins/devin/plugin.json`, `plugins/opencode/package.json`) to the release's own, changed or not (#841): the plugin of switchboard X.Y.Z is X.Y.Z. Claude Code and Codex keep an installed plugin by its `version`, and a pull request does not touch it, so don't bump a plugin's version in a pull request or by hand in a release. Every plugin sends its version to the broker (§49.13), so a new folder under `plugins/` needs a stamped manifest in `PLUGIN_MANIFESTS` (`tests/unit/test_plugin_stamps.py` fails without one). The script stamps them (`stamp_plugin`) and `tests/unit/test_release_script.py` checks it. The broker's expected plugin version is its own package version, so `plugin_versions.py` is not rewritten.

  It then commits `release: vX.Y.Z` on `release/vX.Y.Z` and opens the PR, whose CI runs the full tests and the docs site. Auto-merge (`--auto`) waits for them. It refuses while another release PR is open. Don't change the version, or a marketplace's `ref`, by hand. Agents cut releases when asked ([CLAUDE.md](CLAUDE.md)).
- **Publishing:** merging the release PR runs `.github/workflows/release.yml`, which runs no tests. It tags the merge commit `vX.Y.Z` and publishes the GitHub Release with the version's CHANGELOG section, then the image and the package on PyPI. A tag isn't covered by the ruleset, so GitHub's own token is enough. For about a minute after the merge the marketplaces name a tag that isn't there yet: an update in that minute keeps the plugin that is installed, and a later one installs the release's (Claude Code's next update; Codex's after the next change merges to `main`, or when it lists its plugins). There is nothing to do about it ([DESIGN.md §49.5](docs/DESIGN.md#495-the-plugin-and-connect-an-agent-384)).
- **The image:** after the release, the `publish-image` job (`.github/workflows/image.yml`) builds the new tag for linux/amd64 and linux/arm64. It pushes `ghcr.io/amahpour/switchboard:X.Y.Z`, plus `:latest` if it's the newest release, with a provenance attestation and an SBOM. To rebuild a release's image, for a base-image fix for example, run `gh workflow run image.yml -f version=X.Y.Z`. The package's very first push lands **private**, GitHub's default for a personal account's packages. Switch it to public once, by hand, in the package's settings (Danger Zone, Change visibility). GitHub has no API for that, and it can't be undone. To check without logging in, run `curl -s "https://ghcr.io/token?scope=repository:amahpour/switchboard:pull"`: a public package gets a token, and a private or missing one gets `DENIED`.

- **PyPI:** after the release, `build-dist` builds the sdist and the wheel from the new tag, checks them (`.github/scripts/check_dist.py`: the name and version, the web UI's files and the hook reply table in the wheel, nothing but the source in the sdist, and the wheel installing into a fresh environment and running `switchboard --version`), and attaches both to the GitHub Release. Then `publish-pypi` uploads them to PyPI as `switchboard-chat` with [trusted publishing](https://docs.pypi.org/trusted-publishers/): PyPI accepts an upload from this repo's `release.yml` in its `pypi` environment, so there's no token to store. CI runs the same check on every pull request (the lint job). To publish a release that failed to upload, re-run its failed job; a version that's already on PyPI can't be uploaded again, so a broken one is fixed by the next patch.

**Shards in CI.**
- **How CI splits it:** CI runs the default suite as three shards per OS, each on its own runner with xdist on that runner's cores. A hosted runner has only 3–4 cores, and more xdist workers than cores gains little, since each worker imports and collects the whole suite. So the run gets shorter by using more runners, not more workers.
- **How the shards are balanced:** [pytest-split](https://github.com/jerry-git/pytest-split) balances them by the per-test durations recorded in `tests/.test_durations` (`--splits 3 --group N --splitting-algorithm least_duration`). A test that isn't in the file counts as the average one.
- **Keeping the file current:** when tests are added or their times change a lot, regenerate it and commit it:

  ```bash
  uv run pytest -n auto --store-durations
  ```

- **Locally, nothing changes:** run the suite whole with `-n auto` (pytest-split does nothing without `--splits`). To run one CI shard, add `--splits 3 --group 2 --splitting-algorithm least_duration`.
- **Sharing a machine:** when several agents (or people) work on one machine, the suites run one at a time. `-n auto` starts a worker on every core, and every worker starts brokers and scripted agents; the e2e tests add a Chromium each. Three such runs at once pushed a 30 GB machine into swap until it froze (2026-10-12). Take a lock and cap the workers:

  ```sh
  PYTEST_XDIST_AUTO_NUM_WORKERS=8 flock "${XDG_RUNTIME_DIR:-/tmp}/switchboard-suite.lock" uv run pytest -q -n auto
  ```

  `flock` waits for the run that holds the lock, and the variable makes `-n auto` mean eight workers. On Linux, `systemd-run --user --scope -p MemoryMax=12G -p MemorySwapMax=0 -- <the command>` also caps the run's memory, so a run that grows past it is killed and fails instead of taking the machine down. Before the e2e world lifecycle and scheduling fix, eight workers peaked near 9.7 GiB; with per-test cleanup and three groups for the large module, 3.5 GiB. The existing 12 GiB cap leaves room for other suites. Check that the cap took (`cat /proc/<a test process's pid>/cgroup` names the scope it runs in): a `uv` installed as a snap moves the command into a scope of its own, `snap.astral-uv.uv-<id>.scope`, where that limit doesn't reach. There, cap the scope it landed in once the run has started: `systemctl --user set-property --runtime <that scope> MemoryMax=12G MemorySwapMax=0`. An agent that starts other agents tells each of them the exact command.

  A run that is killed (SIGKILL, the OOM killer, a timeout, a frozen machine) skips the cleanup that removes its temp homes, so it leaves them in `/tmp`, and a tmpfs `/tmp` fills with them (#919). The next run sweeps them (#922, `tests/tmp_homes.py`): at the start of each run, the xdist controller (or the only process) removes each of your own `yk-*` directories directly under `/tmp` that nobody uses, and writes one line with the count (`switchboard test homes: removed N ...`) when it found any. A home's users hold a lock: `make_tmp_home()` takes `flock(LOCK_SH)` on `.switchboard-test.lock` in the home, before it writes the `.switchboard-test` marker, and keeps it until the home is removed, and `SubprocBroker` passes it to its broker and its CLI calls (`pass_fds`), as does every test that runs `switchboard start`, so a broker that outlives pytest still holds it. The kernel drops the lock when the last holder dies, however it dies. A broker `switchboard start` daemonized doesn't hold that lock, so the sweep also takes the broker's two locks: `logs/broker.out` (`Paths.out_log`), on which `switchboard start` takes a shared `flock` before it launches the daemon, which inherits that open file as its stdout and stderr and so holds the lock from launch until it exits; and `run/broker.lock` (`Paths.lockfile`), which the broker holds from just after it makes its directories until it exits. So a home is held by its maker (until `remove_home()`), by any child given its test lock, and by any broker `switchboard start` launched there, from launch to exit, through the lock on `logs/broker.out` it inherits; then `run/broker.lock` too. A starting daemon is never without a holder of its home, even when the run and the CLI that started it are both gone before it takes `run/broker.lock`. No file's contents or age is read (nothing in a file tells a restarting broker from a stopped one): only who holds a lock. The sweep removes a home only if it can take all three locks without waiting, no Unix socket under the home accepts a connection, and nothing under it is unreadable. It checks and removes one directory (opened once, its identity checked again after the locks and just before the last `rmdir`), in place: every entry but the marker and the lock file first, then the marker, then the lock file, then the directory. There is no rename. The `tmp_home` fixture removes its home the same way (`tmp_homes.remove_home()`), so a removal stopped part way (a kill, an error) leaves the home under its own name with its marker and lock file, or the lock file alone: `no_homes_left_behind` fails the run naming it, and the next sweep removes it (a `yk-*` directory whose only entry is the lock file is removed once the sweep can take that lock without waiting).

  Making, removing and sweeping take one lock per user, `/tmp/yk-sweep-<euid>.lock` (opened with `O_NOFOLLOW`, mode 0600, and used only if it is a regular file of yours; another user's never stops yours). The sweep holds it exclusively for its whole pass, and skips the run and says so (`switchboard test homes: skipped, ...`) if it is held or unusable; `make_tmp_home()` holds it shared from before `mkdtemp` until the marker is written, and `remove_home()` from before its first unlink until its `rmdir`. Only a lock file that no process of yours can use (a symlink, a directory or a non-directory in its path, a non-regular file, or a file that opens and is another user's) lets making and removing go on without it, since no sweep can run then either. Any other error taking it makes `make_tmp_home()` and `remove_home()` raise, naming the lock file, without touching a home, and the sweep skips on any error: EMFILE, ENFILE, ENOMEM, EIO, ENOSPC or a failed `flock` are that process's own, and EACCES or EPERM may be too (a sandbox can refuse one process the open while another of your processes holds the lock, #922's seventh round), so another run may still sweep. The cost: if another user leaves a 0600 file at your per-uid name, your tests can't make homes until it is removed. So while a sweep runs no test is part way through making or removing a home, and what it finds half made or half removed a dead process left. That file stays in `/tmp`. The sweep leaves: a home in use; one holding only the marker (a home made before #922 starts that way), or with other entries but not both the lock file and the marker, whatever its name; a `yk-*` symlink; another user's; and an empty `yk-*` directory. That last is the bounded exception: a removal killed between unlinking the lock file and the `rmdir` leaves one, and the sweep never removes an empty directory, because many tests remove their own homes with plain `shutil.rmtree`, without the lock, and their last `rmdir` would fail if a sweep took the empty directory first. The gap between the sweep's last identity check and its `rmdir` is bounded too: `rmdir` removes only an empty directory, `/tmp` is sticky so only you can rename the emptied home and put something under its name, and no test makes or removes a home during a sweep; a process of yours outside the tests doing exactly that in that instant costs at most one empty directory. It never looks at a folder's age, a pid or `/proc`, and nothing it raises stops the run (`tests/integration/test_sweep_killed_homes.py` shows each case). When none of your own test runs is going, your empty `yk-*` directories can be removed, and a home it left that you know is unused (a broker still running from a killed run: stop it first) listed, removing nothing, with the commands below. Not while a run is going: they don't take the sweep lock or any home's lock, so the first can delete a directory a live test has just made (`mkdtemp` makes it empty, before its lock file) or is about to `rmdir` itself, and a home the second lists may be one a live run is using.

  ```bash
  find /tmp -maxdepth 1 -type d -name 'yk-*' -user "$(id -un)" -empty -delete
  find /tmp -maxdepth 1 -type d -name 'yk-*' -user "$(id -un)" -mmin +360 \
    -exec test -f '{}/.switchboard-test' ';' -print
  ```

  A run that ends normally must leave none at all, and the suite checks that it does. Each process (each xdist worker too) remembers the homes `make_tmp_home()` made, and `no_homes_left_behind`, a session-scoped autouse fixture in `tests/conftest.py`, looks for them after every other fixture is torn down: any still there fail the run, each named with the test that made it. Only that process's own homes count, so a run going on alongside never fails yours. A test or fixture that makes a home removes it when it ends (a helper such as the meeting tests' `World` removes the home it was given in `stop()`); one it hands to a child process or restarts a broker on stays until then. `tests/unit/test_leaked_homes.py` shows a leak failing a run, under xdist too.

### Live tests (real agent CLIs, opt-in)

`tests/live/` drives the real Claude Code, Codex, OpenCode V2, Devin, Cursor and Grok Build CLIs over HTTPS ([DESIGN.md §12.4](docs/DESIGN.md) has the design). They are marked `live`, never run by a plain `pytest` (each module skips itself with the line that says how to run it) and never in CI. Each starts a throwaway broker in a temp home, makes an agent token through the web API, and runs one CLI in a private tmux server with the plugin or config from your checkout (OpenCode uses a private standalone server, below). It then plays the person through the web API: the agent joins and says something; an @mention wakes it while idle; one arrives mid-task and is delivered after its next tool call; a subagent's tool calls take nothing meant for the session; quitting shows it offline and resuming brings it back; a killed Devin shows offline; a revoked token ends it.

```bash
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude.py -s -q   # or codex, devin, cursor
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude_long_wait.py -s -q  # message at 315 s, about 6 minutes
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude_signin.py -s -q   # Claude Code signed in through the browser
SWITCHBOARD_LIVE=claude uv run pytest -m live tests/live/test_live_claude_host.py -s -q   # Claude Code hosting the meeting bot, with Docker (below)
SWITCHBOARD_LIVE=claude SWITCHBOARD_MEETING_URL_FILE=<file> uv run pytest -m live tests/live/test_live_claude_mine.py -s -q   # /meeting <link> mine in a real call (below)
SWITCHBOARD_LIVE=grok uv run pytest -m live tests/live/test_live_grok.py -s -q   # Grok Build with your own Grok login
SWITCHBOARD_LIVE=grok SWITCHBOARD_GROK_BASE_URL=standin uv run pytest -m live tests/live/test_live_grok.py -s -q   # with a stand-in model: no login, nothing spent
SWITCHBOARD_LIVE=claude,codex,opencode,devin,cursor,grok uv run pytest -m live tests/live -s -q    # all of them, one after the other (not the meeting self-test, below)
```

To check restart recovery, run the two private scenarios for each harness. Use the shared-machine lock above when sharing a machine.

```bash
SWITCHBOARD_LIVE=claude,codex,cursor,devin uv run --frozen pytest -m live tests/live/test_live_restart.py -s -q
SWITCHBOARD_LIVE=opencode uv run --frozen pytest -m live tests/live/test_live_opencode.py -k restart -s -q
```

These runs stop the throwaway broker for 30 seconds while the agent is listening and while a tool
is running. They use a temporary configuration and home for every CLI, with only a private copy
of its account login where needed.

- **What you need:** the CLI on `PATH`, logged in (`claude`, `codex login`, `devin auth login`, `agent login`), `tmux` and `curl`. tmux is found on the `PATH` pytest was started with, wherever it is installed (Homebrew's `/opt/homebrew/bin` included); the CLIs' own `PATH` is not widened for it. A harness whose CLI or login is missing is skipped with the reason.
- **What they cost:** the cheapest model each account has (Claude `haiku`, Codex `gpt-6-luna`, both at low effort; Devin `swe-1-6-slow`; Cursor `auto`), about a dozen model turns per harness. A run takes 25 to 50 s for Claude Code, about 40 s for Codex (about 0.4 million tokens, nearly all cached input), about a minute for Cursor and about 3 minutes for Devin (it waits out the 130 s a killed Devin takes to show offline; the free plan's quota fell by under 1 percentage point a run). Each ends with a `LIVE RESULTS` block: what each scenario found, and one line of what the run spent, read from the CLI's own record (Claude Code's transcript, Codex's rollout, Devin's quota banner). Cursor's free account may be out of quota: its first test needs no model, and the rest are skipped, with the reason, until a one-word call works.
- **Cursor on macOS:** its live tests skip, except the first (#530). The Cursor CLI keeps its login in the macOS Keychain, not under the home directory, and the run gives Cursor a temp `HOME` (so your own `~/.cursor` is never touched), which cannot see the Keychain. The run does not read or copy the Keychain either, so Cursor looks logged out and every test that needs its model skips with "Cursor is not logged in (on macOS its login is in the Keychain, which the private run can't see; run these on Linux)". Run them on Linux, where the login is a file under `~/.config/cursor`. Don't try to get round it with a `CURSOR_API_KEY` on macOS: print mode works with a key, but the interactive CLI then looks for a Keychain under the temp `HOME`, and macOS shows a "Keychain Not Found" dialog whose **Reset To Defaults** button would reset your own login keychain. Close the dialog with Cancel.
- **The sign-in run** (`test_live_claude_signin.py`, the same `claude` switch, #488) types no token: Claude Code signs the plugin's server in through the browser (`/mcp`, Authenticate), a headless Chromium signed in as the throwaway hosted broker's admin approves it on the consent card, and the scenarios then run on that sign-in: join, an idle wake through the listener key, the key shown to open no tool and no other session, quit, a resume woken before its first turn, and a revoked sign-in. It needs Playwright's Chromium (`uv run playwright install chromium`, as the e2e tests do) and skips with that reason without it. Claude Code runs with a throwaway `CLAUDE_CONFIG_DIR` that holds a copy of the account's login only (0600, deleted with the run), so nothing in the real `~/.claude` changes.
- **The host run** (`test_live_claude_host.py`, the same `claude` switch, #623) is the sign-in run asked to host the meeting bot on this machine through the plugin's `host-meeting-bot` skill and `bin/meeting-host`, as a setup check: no link, `--no-join`, so **no call is joined and no meeting is made or touched**. It checks what the model's command looked like once Claude Code had filled in the skill's placeholders, that the script found the listener key from Claude Code's pid and registered the call, that the real joinly and a relay built from your checkout come up (joinly with no address of its own), and that End call makes the relay exit 0 and joinly stop with it. It needs Docker with Compose and the joinly image (`docker pull ghcr.io/joinly-ai/joinly:v0.5.4@sha256:d19ca294eb24625d69d8069d0168cb5214af3652fbf721eb07480177eb4b9ea0`, which the test never pulls), builds switchboard's image from the checkout (or `SWITCHBOARD_LIVE_RELAY_IMAGE` names one), and fetches the two joinly fixes unless `SWITCHBOARD_LIVE_FIXES_DIR` holds the pinned files (it checks their sha256). It leaves no container behind, even when it fails.
- **The handoff run** (`test_live_claude_mine.py`, the same `claude` switch, #623) is the host run in a real call: the person types `/meeting <link> mine`, and the model, woken by the room's message, runs the skill with `--from-room`, so the link reaches the script from the broker and never the model. The relay joins the call, the meeting's id is checked to be in no transcript, database file, room message or relay log, and End call and `stop` leave nothing running. It needs what the host run needs and a Zoom link in a file of mode 0600 (`SWITCHBOARD_MEETING_URL_FILE`); the `meeting-self-test` skill's steps 2, 3 and 5 make the meeting, write the file and delete both. Nobody needs to be on the call.
- **Claude Code's long-wait run** (`test_live_claude_long_wait.py`, #558) asks for a 600 s wait and posts a message 315 s into it, past both the 120 s background threshold and the former 300 s idle cutoff. It checks the broker's delivery record and the settled agent's reply: one wait delivery, no retry and one answer. It takes about six minutes and uses a private `HOME` and `CLAUDE_CONFIG_DIR` with a copy of the account login only; configuration, transcripts and plugin data stay in the temporary home. If Claude Code asks to sign in, stop the run and sign the CLI in separately before trying it again.
- **What they touch:** a temp directory per run, which they remove. Claude Code, Devin and Cursor use the real home for their logins only: Claude Code writes its transcripts and a `~/.claude.json` entry there (the run deletes its transcripts; `~/.claude.json` is reported, not failed). Codex gets a temp `CODEX_HOME` with a **copy** of `~/.codex/auth.json` (mode 0600, deleted at the end, never printed); Codex may rotate a refresh token in the copy, so run Codex's live test only when you can log in again. After a run the md5s of the real `~/.claude/settings.json`, `~/.codex/{config.toml,hooks.json}`, `~/.cursor/{mcp,hooks}.json` and `~/.config/devin/*.json` must be what they were, or the run fails. No approval is ever given: a prompt that appears is declined with Esc.
- **Codex hook trust (0.166.0):** the test-only setup reads `hooks/list` from its private app-server. A composite `currentHash` is `definition/content`: it writes the halves to `trusted_hash` and `trusted_content_hash` under that hook's `hooks.state` key in the temp home. A single hash uses `trusted_hash` alone. Writing the composite into one field leaves the hook modified and stops the TUI at review (#635); no review prompt is answered.
- **Trying a plugin change:** `SWITCHBOARD_LIVE_CLAUDE_PLUGIN`, `SWITCHBOARD_LIVE_CODEX_PLUGIN` and `SWITCHBOARD_LIVE_CURSOR_PLUGIN` name a plugin folder to use instead of the checkout's, for a change that isn't a plugin version yet, or to see a scenario fail against a plugin with a hook taken out. `SWITCHBOARD_LIVE_KEEP=1` keeps the run's temp directory (the broker's log and database; not the Codex login).
- **A failure** prints the CLI's screen, the broker's log, Members, the engine's last events and the run's processes. Every wait has a deadline and none sleeps to mean "by now". A live test that fails sometimes is a bug in the test or in the product (the first is fixed, the second gets an issue): never re-run it until it passes.
- **Grok Build** (`test_live_grok.py`, #851) runs the real `grok` TUI with this checkout's `plugins/grok` copied into a temp `HOME` of its own (`grok-home`, mode 0700). Grok works in `<home>/ws`, a folder under that home, and the copy of your login is `<home>/.grok/auth.json`, outside it, so it is never in Grok's workspace. Grok Build 1.0.92 asks once at start-up whether to trust `ws`: the driver answers `y` for that folder only, as it answers Claude Code's trust dialog for its scratch folder, and Grok keeps the answer in the temp home. Nothing passes `--trust` or writes `trusted_folders`, and a trust question about any other folder, or after start-up, fails the run unanswered. Your `~/.grok` (config, plugins, trusted folders) is never read or written. The temp config turns the plugin on, turns telemetry and trace uploads off (`[features] telemetry`, `[telemetry] trace_upload`), starts in ask mode, and allows switchboard's tools and the scratch script, with an `ask` rule for the one command the approval scenario needs. By default the model is your Grok login: a **copy** of `~/.grok/auth.json` (mode 0600, deleted first at the end), or `XAI_API_KEY` if set. `SWITCHBOARD_GROK_BASE_URL=standin` runs the scripted stand-in model of `tests/fakes/grok_model.py` instead, through Grok's `[model.<id>] base_url` (any other value is a chat-completions URL of your own); that run takes about 20 s and spends nothing. With a real login it is five scenarios of a few model turns each, on your plan. The scenarios: join and say, an idle wake, busy then idle with a mention mid-task, waiting for approval not woken (the driver cancels the prompt with Ctrl+C, never approves), quit shows offline. `SWITCHBOARD_LIVE_GROK_PLUGIN` names another plugin folder to try.
- **Run them** when a change touches `plugins/`, `adapters/https.py`, the hook replies or the engine's delivery to a harness, and say in the pull request what they printed. `tests/unit/test_live_harness.py` runs on every run and checks everything about them that needs no model.

**OpenCode V2** (#513) has a separate private-server test:


**The meeting self-test** (#600) is a live test of a different kind: no agent CLI and no model, but a real call. It starts two [joinly](https://github.com/joinly-ai/joinly) containers (switchboard's meeting bot, and a test speaker named `switchboard self-test speaker`) and a throwaway broker in a temp home with a room and a scripted agent, `claude-1`. Both bots join one Zoom, Meet or Teams call and seven steps run in order, each recording pass or fail, what it expected, what it saw and how long it took: the room's bar goes live; a sentence the speaker says reaches the room as a call line; "Claude one, can you hear me?" wakes `claude-1`; with voice on, `claude-1`'s `@call` line is heard by the speaker; `/meeting snapshot` stores a JPEG and posts its card; the speaker says a line in each of two voices and the bot hears both; `/meeting leave` ends the bar and no bot is left in the call. The design is in [DESIGN.md §12.4](docs/DESIGN.md) and the features it checks are in the [meetings guide](docs/guide/meetings.md).

```bash
SWITCHBOARD_LIVE=meeting SWITCHBOARD_MEETING_URL_FILE=<file> \
  uv run pytest -m live tests/live/test_meeting_selftest.py -s -q    # three to six minutes, no model
```

- **The easy way is the skill.** [`.claude/skills/meeting-self-test`](.claude/skills/meeting-self-test/SKILL.md) makes a 15-minute Zoom meeting with the Zoom connector, writes its link to the file, runs the test under the machine's lock, deletes exactly that meeting and the file even after a failure, and reports the table. By hand, make any Zoom, Meet or Teams call yourself; for Meet or Teams someone has to admit both bots as they ask to join.
- **The same test with a hosted bot** (`tests/live/test_meeting_selftest_hosted.py`, #623) has two tests under the same switch. Without a link, one checks that a hosted bot starts and stops cleanly (the plugin's script, the real joinly and a relay, End call, `stop`; no call, no meeting, no model). With the link file, the other runs the six steps with the bot started by `meeting-host`, here or, with `SWITCHBOARD_SELFTEST_HOSTED=remote`, on another machine such as one with a GPU: it prints the commands to run there, and that machine reaches the throwaway broker through an SSH tunnel. `SWITCHBOARD_SELFTEST_DEVICE=cpu|gpu` forces the device. The module's docstring has the whole procedure.
- **What you need:** Docker with the joinly image pulled (`docker pull ghcr.io/joinly-ai/joinly:v0.5.4@sha256:d19ca294eb24625d69d8069d0168cb5214af3652fbf721eb07480177eb4b9ea0`, 3.7 GB) and a call whose link you can put in a file. Zoom must let guests join from a browser, with no forced waiting room or sign-in; the skill lists the settings.
- **On Zoom, both bots run with the speaker-name fix** (joinly-ai/joinly#187), the file DEPLOY.md pins, fetched and checked by its sha256 and mounted read-only, because stock 0.5.4 can't read Zoom's participant list. **On every platform, both also run with the first-word fix** (#620), a second file pinned and checked the same way: without it joinly clips the first word of a line, and the hotwords can turn it into "Claude". **On every platform, both also run with the voice patch** (#713), two files of this repository's `deploy/joinly/` checked by their sha256, which step 6 uses: the speaker says a line in each of two Kokoro voices and the bot must hear both, and a line in an unknown voice must fall back. `SWITCHBOARD_SELFTEST_STOCK_JOINLY=1` runs stock joinly, without any fix (and without step 6). `SWITCHBOARD_SELFTEST_CALLOUTS=N` says step 3's call-out N times in the one call (up to 30) and reports how many woke the agent, to measure a rare miss (#602). `SWITCHBOARD_SELFTEST_OBSERVER=1` adds a third joinly that only listens: when a call-out doesn't wake the agent, the report says what this independent listener heard too, which tells a loss in the bot from a loss in the call's audio (#602). A failed step keeps both containers' logs, scrubbed of the link, in the output folder, and `meeting-selftest.md` names the files. `SWITCHBOARD_SELFTEST_LOGS=1` keeps them on a pass too. Delete the logs after reading them: they name the call's participants.
- **The link is a secret.** It carries the call's passcode. It comes from the file named by `SWITCHBOARD_MEETING_URL_FILE`, which must be a plain file of mode 0600 (anything else is refused, and the message never quotes it), never from an argument. The test keeps it out of every output: it prints as a placeholder, errors that might quote it are scrubbed, the report is checked for it, and at the end the broker's database, messages and log are checked for any piece of it. Delete the file when you are done.
- **The result** is printed as a table and written, as JSON and Markdown, into `$SWITCHBOARD_SELFTEST_OUT` (or a temp folder the run names). A step with words passes on 60% of the expected content words, because speech-to-text of text-to-speech is close, not exact; a step that can't start because an earlier one failed counts as failed. The test fails if any step does, and names them.
- **Whatever happens,** both bots leave the call and both containers are removed, also when the run is stopped with SIGTERM. A run killed harder can leave containers: `docker ps -a --filter label=switchboard-selftest` lists them, and `docker rm -f <name>` removes one.
- **`SWITCHBOARD_LIVE=all` does not include it.** It needs a call, and a call needs an account, so only `meeting` runs it. A plain `pytest` skips it with the line that says how. `tests/unit/test_meeting_selftest.py` runs on every run and checks everything about it that needs no call: the word comparison, the link file's checks, the scrubbing, when a failed step keeps the logs, and the report. It never runs in CI.

### Plugin and server compatibility (opt-in real run)

The oldest release of the major is also run for real, locally (#850). It needs the release's git tag in your checkout (`git fetch --tags`) and `curl`, and no network or Docker; CI does the offline half on every pull request (it fetches the tag itself):

```bash
uv run pytest -m compat tests/compat   # the newest plugin's listener against a real v1.0.0 broker run from its tag
```

When the major goes up, move `tests/fixtures/compat/` and the tag the `Fetch the oldest release` step in `.github/workflows/test.yml` fetches to the new major's first release.

### Evals (real agents, graded from the database, opt-in)

`tests/evals/` asks what the live tests don't: not whether the plumbing works, but what a model does with the room's rules. A scripted person plays against three real Claude Code agents in a throwaway room ([DESIGN.md §12.7](docs/DESIGN.md)), each run is graded from the broker's database, and a scenario repeats k times because agents aren't deterministic. Use it to see whether a change to the text agents read (`ROOM_RULES`, the join text, a room's own rules) or to who a message wakes makes a difference, before and after. It never runs in CI or by default (the module skips itself with the line that says how to run it), and a harness error (a timeout, a crash) is counted apart from a failed check.

```bash
# five scenarios, Claude Code only: three about who answers (#480), review-board (#629) and board-draw (#725)
SWITCHBOARD_EVAL=claude flock "${XDG_RUNTIME_DIR:-/tmp}/switchboard-suite.lock" \
  uv run python tests/evals/run_evals.py run --arm baseline --k 5
uv run python tests/evals/run_evals.py list                      # the scenarios and their checks
SWITCHBOARD_EVAL=claude uv run pytest -m eval tests/evals -s -q  # one real trial, as a smoke test
```

- **What you need:** `claude` logged in and `tmux` on `PATH`, as for the live tests. Real CLIs in tmux are heavy: run one eval at a time, under the same lock as the suites ("Sharing a machine").
- **What it costs:** Measured on 2026-10-22 (Claude Code 2.1.307, `haiku` at low effort, tokens priced at the published rates): a trial takes about 32 s (12 to 21 s from the question to a settled room; the rest is three CLIs starting and joining) and costs about 1.3 cents, 0.54 to 0.77 million tokens, nearly all cache reads, of which 0.2 to 0.45 million come after the question. Twenty-five trials (the first experiment, #480) took 13 minutes and 32 cents. At the published rates `sonnet` costs twenty times as much a token. Each run is capped: a trial stops at `--token-cap` tokens (3 million by default, all of an agent's tokens, cache reads included) and the whole run at `--max-cost` dollars (1.00 by default), and the room's wake budget and loop guard are on. The run prints each trial as it ends and writes `tests/evals/_results/<arm>-<time>.json`, which git ignores; the file has the cost.
- **What it touches:** what the live tests do: a temp directory per trial, the real home for Claude Code's login only, transcripts deleted with the trial, and `~/.claude/settings.json` checked before and after (a change stops the run). No approval is ever given: a prompt that appears is declined with Esc and counted.
- **Try a change:** run the baseline **twice** (the spread between two runs of the same thing is the noise a change has to beat), then the same command with the change on its own arm. The room's own rules (#105) change what agents read without touching the code: `--rules "When nobody is named, only the agent whose name sorts first answers; the others pass()."` or `--rules-file`. For a change in the code or a plugin, check out that change and run the same command.

  ```bash
  uv run python tests/evals/run_evals.py compare tests/evals/_results/baseline-1-<time>.json \
    tests/evals/_results/first-answers-<time>.json --repeat tests/evals/_results/baseline-2-<time>.json
  ```

  `compare` prints each check as `4/5 -> 5/5` (of the trials that were graded) with the harness errors beside them, then the change in tokens after the question, cost, wakes, wakes that ended in a `pass()` and posts, each against the spread of the two baseline runs: it says **REAL** only for a change larger than that spread. Without `--repeat` nothing is called real. Iterate on the cheapest model (the default `--model haiku`), and confirm a change that matters on the model people use (`--model sonnet`, twenty times the price a token).
- **Add a scenario:** a file in `tests/evals/scenarios/<name>.toml` with the room, the `agents`, the person's `[[steps]]` (`say = "..."`) and `[[checks]]`: each has an `id` (its name in the results), a `grader` from `tests/evals/evalkit/graders.py` and that grader's arguments. A scenario that names a grader, argument or agent that doesn't exist is refused when it is read (`run_evals.py list` reads them all). Then add the scripted rooms that fail and pass each of its checks to `ROOMS` in `tests/integration/test_evals_graders.py`: the regular suite fails if a check has no pair. A new kind of check is a function in `graders.py` that takes the run record and returns a `Result`; it reads the store, never what an agent said, and no model judges.
- **What it doesn't measure yet:** a trial ends when the room has settled: every agent idle, nothing addressed to an agent waiting, nothing moving for 8 seconds. Chatter that addresses nobody waits in the engine for its hold (`unaddressed_hold_s`, 270 s, [§8.2](docs/DESIGN.md)) and is not waited for, so the wakes it causes later are not counted. Codex and the other harnesses, nightly runs and a judge are later slices (#480, #119).
