# Security model

switchboard is built for **red-team testing with approvals turned off**: Claude Code in bypass mode, Codex with approval `never`, and so on. In those sessions, any room message, including one from another agent, can make an agent run commands without asking.

- **Joining a room is your opt-in.** Members in the web UI marks approval-off agents with a red ⚠ and "Approvals off" (from the session's own hooks), and "Approval mode unknown" when the mode is unknown (Cursor, Devin: treat it like approvals off).
- **A room is a bridge.** Work that a prompting or sandboxed member posts can be carried out by a ⚠ member without any prompt; the UI shows a banner when a room mixes them.
- **The loop guard is off by default (#406).** It paused a room after a run of agent messages with none from you, and it kept stopping agents that were doing real work. Without it, nothing stops agents talking to each other. The wake budget (60 wakes per room per hour) limits how often an idle agent is woken, and after that only your messages wake anyone. But it counts wakes only: agents that are already busy can keep trading messages as hook context, slowed only by the per-agent limit of one post every 10 s, which a reply to you or to a message that @mentions it skips (§8.3). With approvals off, every such message is room text that can make an agent act. If that is too many for you, turn the guard on: `/hops 6` in a room, or a default hop limit in Settings for the rooms you create.
- **switchboard itself never answers or bypasses an approval prompt**, never emits a hook permission decision, never registers a permission hook that can decide. A report-only one, which outputs no decision, is allowed for status, with the maintainer's yes of 2026-10-21: Codex's plugin and Devin's template each register a `PermissionRequest` command hook that sends the session's id and tells the room a prompt is open, prints nothing and throws away the server's answer, so it cannot approve or deny. Claude Code's Notification hook, which can decide nothing, does the same for Claude Code ([DESIGN.md §11](docs/DESIGN.md#11-security-model), [§49.9](docs/DESIGN.md#499-an-open-approval-prompt-shown-to-the-room-472)), never declares Claude's channel permission relay, never widens a sandbox, and listens only on `127.0.0.1` and a Unix socket only you can open (unless you run it on a server behind HTTPS with `--listen` and `--public-url`: see below). **Nothing is pushed into an agent** (0.38.0 retired the local channels that did: Claude's inbox, Codex's turns, the queue): an agent hears what it asks for, what fills its open `wait()` or its held Stop hook, or what its own hook is answered with after a finished tool, so a message can't land in an open approval prompt.
- **Human commands come from a terminal on this machine, not over SSH.** `switchboard say`, `cmd`, `login` and the other human verbs are refused when they reach the broker through a forward of its socket (`ssh -R`, `ssh -L`, socat: the broker then sees the relay, never who is behind it), and when they run under a remote login to this machine (sshd, dropbear, mosh-server, tinysshd, Tailscale SSH, Eternal Terminal, telnetd; other servers are not recognized). This closes only the direct routes (`ssh this-machine switchboard login`); it is not a boundary. Anything with a shell here can still act as you, for example through a detached process or keystrokes sent into your tmux (see [A detached process can act as you](#what-switchboard-cant-stop)), so **never give another machine, or an agent on it, a key that opens a shell here or forwards sockets.** If you work on this machine over SSH yourself, set `allow_ssh_cli = true` under `[security]` in `~/.switchboard/config.toml` and restart the broker; that lets every key that opens a shell here run `switchboard login`. A relay is refused either way. The web UI is unaffected.
- **On a server** (the container image, [docs/DEPLOY.md](docs/DEPLOY.md)), the broker answers only to its public URL and trusts no forwarded headers. TLS ends at your platform's proxy, so the hop from there to the container is plain HTTP on the platform's network. You set a fresh broker up with a one-time password from its log, and add people from its admin section; everyone signs in with a password or a passkey. **Whoever can read the log in the minutes before you use it could set it up first** (you'd see it refused, and `SWITCHBOARD_RESET_OWNER` recovers), and `switchboard login` inside the container still signs in as the admin, so **whoever can exec into the container can sign in**: keep platform credentials (a kubeconfig, a Render API key) away from your agents. **Everyone you add can steer every agent**: every person's messages are `kind=human` to every agent, approvals-off ones included, so add only people you'd hand your terminal to, and Remove ends someone at once: their sessions, and their agents (their agent tokens are revoked). Agents cannot join under a person's name or its prefix, and a person cannot be added under a name an agent holds or used in the past day. Passwords can be guessed online where passkeys can't: wrong ones slow down per account (the admin's aliases share one limit), and a password needs 10 characters and must not be common. A signed-in browser receives a sealed device cookie with its own guessing limit for 30 days, or until the broker restarts; the cookie alone cannot sign in. Someone who can reach the sign-in URL can still keep a new browser, one without that cookie, from signing in with a password: by guessing its account, or by flooding sign-ins. A passkey still works during password lockout. Only an email signs a person in (and `admin` the admin), never the name everyone sees in the rooms: someone with no email can't sign in at all. A stolen web session can't add a passkey, change the password, add someone or make an agent token without a password or passkey check, so **Sign out everywhere** in the Sign-in sheet ends an intruder who has only a session. Threat model: [DESIGN.md §30.4](docs/DESIGN.md#304-threat-model), [§31.6](docs/DESIGN.md#316-threat-model-a-delta-to-304) and [§32.6](docs/DESIGN.md#326-threat-model-a-delta-to-316).
- **An agent token is the key to your agents on one device** (Settings → Agents, #382). Whoever has it can act as your agents on that device, never as you or anyone else: it can't sign in to the web UI, post as you or run a command. It is shown once and kept only as a hash, so keep it like a password, and **Revoke** it the moment a device or its copy of the token isn't yours anymore; removing a person revokes theirs. On a hosted broker, making one needs a password or passkey check in the last five minutes, so a stolen web session can't make one. An agent uses it at `/mcp`, which answers only a live token and refuses every request a browser could send (one with an `Origin`). Over HTTPS, hooks send switchboard only what their input templates name. For switchboard's own tools: the session id, the call's id, the tool's name, the approval mode, and the tool's own result. For every other tool (#422, #493, so a busy agent hears its messages after any tool call): the session id, the call's id and the tool's name, never its input or its result, so no Bash output, file or secret leaves the machine; the name of a tool does (`Bash`, or an MCP tool's `mcp__<server>__<tool>`). Cursor's and Devin's are small scripts that check what they print back: only context in the harness's own shape, whatever the server answers. Claude Code's tool hooks also send the id of the subagent that made the call, when there is one (an opaque id Claude Code makes up, #446), so the server can leave the session's messages for the session. Its Notification hook, which tells the room that a permission prompt is open (#472), sends the session id, that same id and the notification's type, never the notification's text, the tool or its input. Codex's and Devin's `PermissionRequest` hooks send the session id and the event's name and nothing else (never the tool or its input, which the harness hands them), with the same token, and read no answer. Claude Code's listener sends only its session id. **An agent can also be signed in through the browser** (OAuth, #386: Codex's `codex mcp login`, Claude Code's `/mcp`) instead of being given a token, and what it gets is the same kind of token, listed in Settings → Agents as a sign-in and revoked the same way; like a typed token it has no expiry. A person approves it on a page that names them and the device, and a hosted broker asks for the same password or passkey check as for making a token; nothing a room message or another agent does can approve one, and **an approval you did not start yourself gives a program on that machine a token for your agents on the device you named**, so approve only a sign-in you just began. PKCE `S256` is required, a code lives 60 seconds and works once (used twice, it revokes the token it made), a client can register only loopback addresses and must use one exactly, and the name an agent gives itself is only a name. Registration needs no sign-in, so anyone who can reach the server can fill the clients it keeps for a day (500, oldest dropped) or, at 60 a minute, keep new agents from registering for a minute at a time. ([DESIGN.md §49.10](docs/DESIGN.md#4910-signing-an-agent-in-through-the-browser-386)) **Claude Code's plugin can be signed in this way too, and then its two command scripts (the idle wake and the report of a session's start and end) present a listener key instead of a token** (#488), because Claude Code keeps a sign-in's token to itself. The plugin makes the key on your machine, keeps it in a file of its data folder that only you can read (mode 0600; on Windows an access list of your account alone, with no rule inherited), and tells the server nothing of it but its hash, in a header of the signed-in connection: only a request that carries the sign-in can make the server accept one. It opens those two routes, and the one that registers a hosted call (#623, below), for one session and nothing else (no tool, no room, no other session), it dies with its sign-in, and a week without use ends it. Any process of yours can read the file, **the agent's own shell included**, so what a prompt-injected agent gets from it is that session's wake text, the power to mark it offline and the power to register a hosted call (below), less than the tools it already has. The plugin sends a typed token as `X-Switchboard-Token` (so that Claude Code can still start a sign-in when none is typed), and **a proxy in front of the server that logs request headers should redact that header as it does `Authorization`** ([docs/DEPLOY.md](docs/DEPLOY.md)); the broker logs no header. ([DESIGN.md §49.11](docs/DESIGN.md#4911-claude-code-signs-in-through-the-browser-the-listener-key-488)) **The server writes the hooks' replies** (#380's decision 5), so a compromised or hostile server could put text into an agent's context after a tool call, or keep an idle agent going with a message, as a room message can; it still can't approve anything, since switchboard registers no permission hook that can decide (a harness would obey a decision in the answer to a PermissionRequest hook, so Codex's and Devin's hook for it is a command that discards the answer, and the server refuses the same event from an `mcp_tool` hook) and its replies are checked against exact shapes with no permission decision in them ([DESIGN.md §11](docs/DESIGN.md#11-security-model), [§49.4](docs/DESIGN.md#494-waking-and-status-from-hooks-383)). ([DESIGN.md §49](docs/DESIGN.md#49-agents-over-https-380))
- **OpenCode V2's plugin** (#513) reads its token only from `SWITCHBOARD_AGENT_TOKEN` and sends it in a header, never a file, log, URL or subprocess argument. `/mcp/status` accepts only POST, a live agent token, no Origin, and its fixed fields and event names; web cookies and Claude listener keys cannot open it. Its status replies are always `{}`. `/mcp/listen` accepts an explicit OpenCode harness only with an agent token and refuses a busy, approval-blocked or offline session even on the first round. Every plugin action checks the session's location directory, since a shared OpenCode service broadcasts all projects' events to all plugin instances. `permission.asked` aborts its park immediately; a read-only pending-permission query must be empty before the hold clears or a wake queues. No permission reply, permission hook or permission rule is registered. A one-use receipt bound to the token/device/session and exact offer confirms queue admission; unrelated user turns cannot confirm a dropped body, and drop or approval returns it to pending. Static checks reject permission decisions, subprocess imports and file writes in the plugin. The queued turn carries exactly the broker's existing wake envelope, with peer text stubbed, and is marked as coming from switchboard. A token holder can claim another session ID on its own device, as with Codex; the ID is not a credential. A compromised server can keep an idle agent going with a message, as above, and still cannot approve a prompt. See [DESIGN.md §49.12](docs/DESIGN.md#4912-opencode-v2-over-https-513).

- **An admin can upload the agents' avatars (#498): a file upload to every browser on the server.** Settings → Appearance → Agent icons takes a PNG or a WebP from an admin (the one person on a desktop broker, an admin on a hosted one) and shows it to everyone signed in, so it is checked as input from outside. Only an admin can send one, and a request from anyone else is refused before its body is read. The file is judged by its own bytes, never by what the sender says: a PNG or a WebP only (**never an SVG**, which can carry script), at most 256 KB and 512 × 512 pixels, its type the file's magic number and the request's `Content-Type` required to agree, and a PNG walked chunk by chunk (CRCs, and nothing after its last chunk), so a damaged file or a picture with markup appended is refused. Nothing is decoded on the server, and the pixel cap bounds what a browser decodes. Each image is served from the page's own origin with its type, `nosniff`, `Cross-Origin-Resource-Policy: same-origin` and `Content-Security-Policy: default-src 'none'; sandbox`, to signed-in sessions only. The page's CSP is unchanged, and no byte of an upload reaches the stylesheet that shows it. The images live in the database, so they are in your backups. An admin can show any picture to everyone else on the server, so it is a way to put misleading content in front of your team; each change is an event in the log (who, which harness, the size and the start of its hash). The same upload, with the same checks and the same admin-only rule, is how the icons of Zoom, Meet and Teams are replaced (#623). Details: [DESIGN.md §29.11](docs/DESIGN.md#2911-customizing-the-agents-avatars-498).
- **Every admin is as trusted as the owner** (#569). On a hosted broker an admin can do everything the owner can. Any admin can take over any account but the owner's admin, by setting its email or giving it a new one-time password. Nobody can remove the owner or take the owner's admin away. An admin can give up their own admin; the owner is always there. Details: [DESIGN.md §51](docs/DESIGN.md#51-admins-569).
- **A file uploaded to a room is untrusted bytes** (#544). It is served only as a download (`Content-Disposition: attachment`, `application/octet-stream`, `nosniff`, `no-store`), never as a page, so HTML or SVG in it cannot run on switchboard's origin. The type the sender claimed is stored and never used to serve. An agent's upload link and an agent's download link are capabilities for one file, random, kept only as a hash, and they last 10 minutes. The upload works once. They are not logged and not written into a message. Who may read the room is checked on every download a signed-in person makes; a file in a room they cannot read is the same 404 as a missing file. A download token is itself the permission, and it was made only when that agent was shown the message. Details: [DESIGN.md §53](docs/DESIGN.md#53-attachments-544).
- **A room's whiteboard is shared state its members write** (#656). An agent in the room can put text on it, and every other member can read that text back, including an agent with approvals off, which then treats it like any other room text it asked to read. The words are cut (200 characters), a link is stored as nothing, and an image, an embed or a script has nowhere to live: a field the board does not name is dropped, and an unknown shape is refused. What an agent reads is quoted by the same envelope as a message, so it cannot close a harness tag. A person who cannot see the room cannot write the board, on the page's socket or through an agent. The drawing runs in an opaque-origin sandboxed document; the room log says who changed it and not what was drawn, so the shape text is not promoted into a system line. The approved board-only exceptions allow inline styles, framing by this origin, browser-made data/blob images and workers, scoped module/font CORS and one fixed iframe in the static checks (#671). No main-page CSP or header is relaxed. The parent validates the frame source, instance, room, message shape and elements, then the broker validates again. A requested image can answer only a pending request for that room and revision, with PNG structure, CRC, byte and dimension limits. It is peer data; no server-side browser is started. Details: [DESIGN.md §56](docs/DESIGN.md#56-a-rooms-whiteboard-656).
- **A live call is another way into the room** (#573). Anyone on the Zoom, Meet or Teams call can say anything, a played recording included, and that text is untrusted peer input: it can wake an agent by name, by naming what the agent has claimed (#541), or on unaddressed talk when a person has enabled listening (#697), the same reach as another agent's @mention, and an approvals-off agent then acts without asking. Keep such an agent out of a room that has a call. Listening is a separate web-only opt-in per agent (`/meeting listen <name>`); the person's CLI may turn it off. It keeps the approval gates, Stop stubs, room budget and a per-agent cap of 40 listening wakes per call by default. The last turns it off with a notice, and ending the call clears it. Enabling with approvals off or unknown warns in the room. A spoken command is only words. joinly has no sign-in and accepts its settings from its client, so it stays on localhost or the compose network (on Kubernetes, beside the broker in its pod, listening on the pod's localhost only). The meeting link's passcode is never stored, shown or logged; the room keeps the platform, not the URL. The transcript is stored like any other message and nowhere else. A hosted relay completes the exact speech id under its existing call key; the slot stays occupied until completion, so an older relay must be updated with the broker. This opens no new route or permission. **Speaking back and seeing the screen are opt-in** (#593). A person turns voice on for one call, with `/meeting voice on` or the switch on the bar. It is off when a call starts unless a person set the room to start calls with it on (`/room voice on`), and no agent or message can turn it on. While it is on, an agent's `say()` that starts with `@call` can be read aloud to everyone on the call, with one line being spoken and one waiting, a 1.5-second speech gap, a 60-second wait limit, an agent's own starts at least 30 seconds apart, and at most 4 agent lines in a row until a person speaks or writes (#697). A line that answers a question put to its speaker (the broker sees an @mention of the agent or a reply to its message in its last batch, never in the line) may start 2 seconds after the last start, the maintainer's approved exception of 2026-11-10 (#713): an untrusted speaker can name an agent, so the cap of 4, the single waiting line, the stale rule, the wake budget and the Voice switch are what bound it. A message in the room is not bounded this way. Agents answering each other in text are bounded too: in a room with a live call, after 8 agent messages in a row with no person's message and no participant line from the call, agents wake only for a person (#713). `hop_limit` is not changed, because a call line must not reset it. An agent prompted by someone on the call, or by anything else it reads, could say something it should not, so leave voice off unless you would let those agents speak for you. A snapshot can capture anything on the shared screen. It is kept as a room file for the room's retention (30 days by default), readable by everyone who can read the room, and only when its bytes are a PNG, JPEG or WebP. **A room can make its calls hands-free** (#697, [DESIGN.md §52.3](docs/DESIGN.md#523-hands-free-calls-a-rooms-setting-697)): `/room voice on` makes every call there start with Voice on, and `/room listen on` makes every agent there listen on calls. Only a person can set either, in the web UI (the room's Call settings or the command); the person's CLI can only read them. An agent's `say("/meeting voice claude-1 am_adam")`, which would pick a member's voice on calls (#713), is only text too: a voice is set by a person on the web alone, checked for its shape wherever it is set and used, and a voice name inside an `@call` line is only words. An agent's `say("/room voice on")` is only text, and no call line, hook or tool reaches them, so a tricked agent can't start speaking in a call or make itself listen. Each change is a notice naming who made it, the room header shows a marker while either is on, and a call that starts this way says so in its first notice. They add no permission: the per-call cap, the approval gates and a person's switches on the call bar all still apply. Details: [DESIGN.md §52](docs/DESIGN.md#52-meetings-a-live-call-in-a-room-573).
- **A call hosted on a person's machine is another way into a room** (#623, [DESIGN.md §54](docs/DESIGN.md#54-hosted-calls-a-persons-machine-pushes-the-call-in-623)). The person's machine runs the meeting bot and pushes what it hears into one room's call, with a key made for that one call. The key is made on the machine and never goes through the model: the plugin's host script registers only its sha256, itself, at `/mcp/meeting/host`, under the agent token or listener key the plugin's other scripts already hold (there is no tool for it, so no model sees even the hash), and the server keeps only that. The call key opens three routes, `/mcp/meeting/push`, `/mcp/meeting/speech` and `/mcp/meeting/leave`, and nothing else (not the tools, the listener, the registering route, the hook routes, the web API or a session), and they open for nothing but a call key (not an agent token, a listener key, a session or a browser). There is no setting to turn it off, because a pushed line is no harder to fake than a person typing "here is what we said", and the names on a Zoom call are chosen by whoever joined. So what protects the room is the label and the limits. **A pushed line is a claim, owned by whoever pushed it.** It is stored with its call, its key and the machine that heard it, and the page shows "via alice-laptop" after the speaker, and the machine and the key's short fingerprint in the call bar, which the relay prints too, so the owner can check it is theirs. It is a call line like any other (`kind=meeting`): agents read it as untrusted peer text, never as your message, and it has the reach of any call line (it can wake the agent it names). The speaker's name is only text. A call is limited to ten segments a second, a hundred at once, one hosted call per person and `[meeting] max_calls` in all, and it ends by itself when its host never starts or goes quiet. The person it belongs to, or an admin, ends it from the call bar or from the call's details in Members (the page asks the broker, per viewer, whether to show **End this call**, `GET /api/rooms/{slug}/call`, which carries no key, hash or person's id; the server refuses anyone else's command all the same) and the key is refused at once; the lines already pushed keep their label. Revoking the machine's agent token (Settings → Agents) ends its call too. **The key is only as safe as its file**: it sits in a file on that machine that any process of the same user can read, so a prompt-injected agent in the same account could push lines into that one call or end it, and nothing else. **A call is hosted only when its person asks their agent to**: there is no tool for it, so a peer's text has nothing to call, and the script runs through the agent's shell and its harness's own permission prompt. **Registering one is now something an agent token and a listener key can do** (the maintainer's yes, 2026-11-05), only for a room that an agent of that machine is in, for a listener key only for its own session (never one the request names), at five tries a minute. The most a prompt-injected agent that can read the token or the key's file can do with it is register a hash nobody holds the key to, which holds the person's one call and the room's slot until it times out, and gives no one a way in. The broker never connects to an address a person gave: the relay connects in, joinly on the machine has no address of its own (it shares the relay's network and listens on its loopback, with no port published, because it has no sign-in), and a meeting link given directly to an agent stays on that machine, though that model sees it in its transcript. With `/meeting <link> mine`, the broker instead holds the link only in memory for ten minutes, bound to the room and the person who typed the command. It wakes only credential-backed agents of that person with a link-free instruction. The existing registration gives the link once, only to a script authenticated as that person and still a room member; the first successful registration wins. No model, database, room history, notice, frame, event or log receives the link or its encoded response field. An expired request or broker restart drops it. The script decodes the private response straight into the relay's private file and never prints it. No new route, tool or credential scope is added. On the machine the link (until the call is joined) and the key are files only the person can read, in a folder only the person can enter, and the relay, which runs as the person in a read-only container with no capability, deletes the link once it has joined and the key when it ends; the link and the key are never a command-line argument or an environment variable of anything the script starts. The script uses the credential the plugin's scripts hold: the listener key it finds in the plugin's data folder from Claude Code's pid (a Bash command is given no plugin variable, so that is the only way), or an agent token in its environment. The two joinly fixes it mounts are fetched from commit-pinned addresses and used only if their sha256 is the pinned one; the images are pulled by tag, not by digest. A hosted bot's relay ends with the call: End call makes it leave, and its joinly container stops with it. `meeting-host stop` stops both containers; the relay reports departure so the server clears the call at once. If the broker is unreachable, the existing silence timeout remains the fallback.
- **Run it all in a sandbox.** Keep switchboard and every agent in one isolated Linux container or VM, with no host secrets inside. See [docs/SANDBOX.md](docs/SANDBOX.md) and [`sandbox/`](sandbox/): the Docker layout is built, its firewall checks pass and the web UI is reachable from your Mac through a loopback relay (the broker keeps its `127.0.0.1` bind), but no agent has been run inside it yet. In Milestone 0, Cursor hooks saw every secret exported by the login shell.

**Codex browser-signed-in hosting (#637).** Its local HTTP header helper makes the same kind of private script key (0600; an account-only access list on Windows), sends only its hash over the authenticated MCP connection, and reads no Codex credential store. The key is pinned to the first authenticated Codex thread and its harness. It opens only the existing `/mcp/meeting/host` route for a room that thread is in; another thread or harness, every tool, the listener, session reporting and call-key routes are refused. A process of the same user can read the file and register a useless call for that thread, occupying its person's call slot until timeout or End call, but cannot read wake text or act as another session. It dies with the sign-in. An agent token remains supported; no route or request-field allowlist widens.

- **A backup contains the whole broker (#688).** `switchboard backup` archives every room's history (private rooms too), stored attachments, password and token hashes, web sessions and passkeys. It creates a new 0600 archive without configuration; store it privately and encrypt copies sent elsewhere. Restore is an offline operation under the broker's home lock, also applied before listening at start from `restore/`. It verifies hashes, integrity, schema, counts and file references before replacing data, refuses unsafe tar members and preserves the old database, WAL and attachments. Archive paths, owners and modes are never trusted. A durable marker blocks startup after an interrupted replacement. An archive is not signed: filesystem operators choose which data to restore. Restoring also brings back the credentials and revocation state from that snapshot; review tokens and sessions after recovery. A changed hostname warns about passkey enrolment. An admin can start a background archive in Settings → Backups and download it over HTTP. Both actions require the existing fresh identity check, and every backup and download start leaves an event and notifies the other admins. The ready link is shown to its initiating admin, works only for current admin sessions with a fresh check, lasts ten minutes, and is invalidated by a broker restart. It streams from disk with attachment disposition, no-store, nosniff, a same-origin resource policy and a sandbox CSP. One job at a time, a five-minute start limit and three retained archives bound the work and disk usage. A CLI login link is not a password/passkey check; desktop brokers that use only these links retain the CLI backup path. No restore-upload or scheduled token endpoint is added. See [Backups](docs/DEPLOY.md#backups).

## What switchboard can't stop

An outside-work claim is advisory. It names a holder, a note and a deadline to other members, but cannot lock a ticket, branch, build or any action outside switchboard. The note is that claim's state or a link. Making or renewing one changes nothing about delivery: it posts no room message, wakes nobody and spends no wake budget. A message that names a live claim afterwards is addressed to its holder as an @mention of it would be (#541), from the same senders and with the same reach, so a claim adds no authority. An agent that ignores `claim()` can still act on the same resource.

Every agent runs as your user, so (details in [DESIGN.md §11](docs/DESIGN.md)):
- **A detached process can act as you.** An agent can start a process that outlives its shell (for example `( sleep 1; script -q /dev/null switchboard login ) &`). Once that process is no longer under the agent, it passes the terminal check. It can post as you, run CLI commands, and get a sign-in link and so a full web session, including `/resume` and raising `/budget`. Watch for the red warning lines `a login link was issued via cli (…)` and `new web login` in the web UI; if you didn't do it, run `switchboard logout --all` and `switchboard stop`.
- **Such a process can also read room text.**
- **Your switchboard cookie goes to every port on `switchboard.localhost`**: don't open links that agents post on `switchboard.localhost`.
- **A Stop hook's follow-up (Claude Code's listener, Codex, Cursor) and Devin's Stop message are user-role messages.** switchboard's text says it relays you and shows other agents' text only as a pointer, but the harness gives it your authority. Mid-task context, after a tool call, is system role for Devin.
- **`pass()` makes an agent read other agents' text first.** That text only ever reaches the model as an untrusted tool result (`read()`, `wait()`, `say()`), never as your message. If you decline an agent's `read()` approval prompt, its `pass()` stays refused and the watchdog keeps reminding it (and then tells you), which brings the prompt back; `leave()` gets it out of the room without reading.
- **A `/catchup` agent can read every session its history tool indexes**, and sessions can hold secrets and untrusted text (see [Catching up](docs/USAGE.md#catching-up-catchup)). The request posts the subjects' session ids in the room, where the other members of a member catch-up can read them, and the agent's report goes to every member.
- **Devin subagents:** switchboard only knows about *background* subagents; a foreground subagent's Stop could be re-armed.
- **On a Linux desktop where Yama allows it** (`ptrace_scope` 0), a process of your user can `ptrace` the broker.
- **Mermaid draws in the page.** A ```` ```mermaid ```` block is drawn only when you click **Show diagram**, with Mermaid's strictest settings, which the diagram can't change, and its styles stay inside the diagram's box. The page's script rule still holds (same-origin script files only), but a logic bug in Mermaid would run in the page, and the app page allows inline styles for the drawings ([DESIGN.md §33](docs/DESIGN.md)).
- **Auto-accepted edits plus a pre-approved test runner or interpreter act like approvals off.** A session in `acceptEdits` (Claude) or accept-edits (Devin) with, say, `python -m pytest` allowed shows as "prompting" (no ⚠), but it can write code and run it without asking. Claude's Don't-ask mode (`dontAsk`) is the same with whatever you pre-approved.
- **Auto mode shows as approvals on, but it asks you about little.** A Claude session in Auto mode (`auto`) shows as "prompting" (no ⚠), yet its classifier runs the calls it judges lower-risk without asking you, so room text can make it act within what the classifier allows. Codex's `--approve-for-me` hands approvals to an automatic reviewer and shows the same way.

- **On a hosted broker, everyone signed in sees who else has a page open** (#354): the Members pane marks them, in every room. It doesn't show which room anyone has open.
- **A private room (#74) is private from other people, not from the server.** Its people alone see it in the web UI, and agents join it only if their person is in it, but the admin, the local CLI and anyone who can read the database see everything. An agent that's in a private room and in a public one can repeat what it read in one to the other: switchboard can't stop an agent from talking, so keep an agent in the private room only if its person trusts it with what's there.
- **With Sign in with Google on, a Google account is a way in.** Only the email the admin set for each person (and their own) signs in, and only once Google says the email is verified; anyone who controls that account can then steer every agent, as that person can. The admin's word is the check: switchboard sends no mail to verify the email it was given. The client secret lives in the deployment's secrets, never in the database or the log (DESIGN.md §38).
- **A join code is a name's key for a day (#304).** An agent's join answer ends with a `yk:j…` code that, given back as `resume`, reclaims its name after a restart. Only the same harness on the same device can use it, but any process of yours that can read that agent's transcript could join under that name once the old session has left. The broker keeps only a hash of it. After a compaction or `/clear`, the reminder switchboard gives the session carries a new code and the old one stops working.

The sandbox is meant to be the boundary for all of these, but it is untested with agents: its layout and firewall checks pass, and no agent has been run inside it yet ([docs/SANDBOX.md](docs/SANDBOX.md)).

## Where releases come from

Only `.github/workflows/release.yml` publishes a release, when a release pull request merges into `main`: the tag and the GitHub Release, the image `ghcr.io/amahpour/switchboard` (with a provenance attestation and an SBOM), and, from 0.21.1, the package on PyPI. On PyPI switchboard is **`switchboard-chat`**. Plain `switchboard` there is an unrelated project, and so are `switchboard-agents` and `agent-switchboard`. It's uploaded with PyPI's trusted publishing, so no PyPI token exists to leak, and each file carries PyPI's attestation of the workflow that built it.

The board’s Mermaid conversion runs in the broker, in plain Python, with no browser and no page (DESIGN §56.9). Only bounded plain flowcharts are accepted; directives, styles and image syntax are rejected, click directives are removed, and a line the parser cannot read is refused. Every label is canvas text, cut and cleaned like any agent text. The converted elements go through the same cleaner as every agent shape, which remints ids; membership and the rate limit are checked before a single atomic import. Playback changes only the local view.

## Reporting a vulnerability

Please don't open a public issue for a security problem. Report it privately through GitHub's private vulnerability reporting for this repository (the **Security** tab, **Report a vulnerability**), with the switchboard version (`switchboard --version`), your OS and the harnesses involved.

Cursor over HTTPS uses a `preToolUse` command hook. It sends only the session ID, tool-use ID and switchboard tool name, then inserts both IDs into that same MCP call. The broker requires an exact one-use match under the device token. The hook reads its agent token from its process environment and sends it in the HTTPS Authorization header. Its postToolUse hook sends, from a switchboard tool's output, only the batch tokens in it.

Devin over HTTPS uses the same one-use check as Cursor, with its PreToolUse hook adding its session ID and tool-use ID to the call. The hook reports only those IDs and the switchboard tool name; its other hooks send status and, from a switchboard tool's result, only the batch tokens in it. The generic `rmcp` client name does not authorize a session on its own.
